# Backend Systems (Python)

## Tag colors

`Api.set_tag_color(tag, swatch)` updates one trimmed, lowercase, case-insensitive
tag key and returns `{success, tag_colors}`. Swatches are `red`, `orange`, `yellow`,
`green`, `teal`, `blue`, `purple`, `pink`; unknown swatches return an error. `None`
or an empty string clears a color. `get_settings()` includes the validated map.
wLib assigns no colors itself, with one exception: the F95 account import
colors "Watched on F95" Orange and "Bookmarked on F95" Purple once, when they
have no color.

## App log and diagnostics

`core/app_log.py` installs the app log in `main()` after the single-instance check.
`<data dir>/logs/wlib.log` captures stdout, stderr, Python logging, and uncaught
main and worker exceptions while preserving terminal output. The file rotates at
2 MiB (`MAX_BYTES`) with three backups (`BACKUP_COUNT`), `wlib.log.1` through
`wlib.log.3`. Logging is always on and separate from `enable_logging`, which
controls per-game launch output. Logs are local and never exported or synced.
Setup failure prints one warning and leaves the original streams and hooks intact.
Backend and packaged smoke tests do not install logging.

The log also records uncaught UI errors under `wlib.ui` with the source, page
path, error location, repeat count, app version, and stack trace when available.
The backend accepts up to 20 UI error entries per rolling minute. It removes
magnet links and strips queries and fragments from HTTP, HTTPS, WebSocket, and
file URLs in every field. It then caps messages at 2,000 characters, stacks
at 8,000, and other fields at 500, including the truncation marker.

`core/diagnostics.py` keeps copies of renderer stages under a lock and collects
environment facts, paths, database size including WAL, and a game count. Tool
discovery reuses Flatpak-aware host lookups and runner discovery; Windows omits
Wine and Proton. The API passes its existing version and tool helpers into the
collectors, so collecting diagnostics does not construct another API or load games.

- `get_diagnostics()` returns `{success, basic, report_basic}`.
- `get_diagnostics_tools()` returns `{success, tools}`.
- `get_diagnostics_report()` returns `{success, report}` with the full plain-text
  report, replacing the home prefix with `~` and login-name path segments with
  `<user>` (segment replacement skips names shorter than three characters).
- `open_log_folder()` creates the log folder and opens it in the system file
  manager. Errors include the folder path.
- `log_ui_error(report)` accepts an uncaught UI error report and returns
  `{success: true}` even if the log entry is dropped or cannot be written.

Reports contain no game titles, tags, URLs, or notes. The page requests basic
details and slower tool checks in parallel.

## Game catalog client

`core/catalog.py` keeps a read-only copy of the published catalog as
`<data dir>/catalog.db`, with a `catalog.json` sidecar
holding the installed manifest, `last_check` and `last_error`. `Api.__init__`
creates `self.catalog` and starts a daemon-thread check unless the
`catalog_enabled` setting is `"0"` (default on). A check skips when the last one
was under 12 hours ago unless forced, fetches the manifest
(`https://wlib-db.thekirin.net/v1/manifest.json`, overridable with
`WLIB_CATALOG_MANIFEST_URL`), and downloads the snapshot only when its SHA-256
differs from the installed one and its `schema_version` is in
`core.catalog_format.SUPPORTED_SCHEMA_VERSIONS`. The download streams into a temp
file in the data folder, stopping past the manifest size (hard cap 200 MB); then
the hash is checked, `lzma` decompresses into a temp `.db`, which is opened with
`mode=ro` for `PRAGMA quick_check` and `meta.schema_version`, and `os.replace`
installs it. The sidecar also records `catalog_sha256`, the SHA-256 of the
installed `catalog.db`; an unchanged snapshot downloads again when the file on
disk fails `quick_check` or no longer matches that hash (a sidecar without it
records the current file). Failures keep the old catalog and are only recorded in the
sidecar. Requests are plain GETs with a `wLib/<version>` user agent and no query,
cookies or library data. The app keeps no connection to `catalog.db` open and
never writes the library database here; library export and sync do not include
the catalog.

- `get_catalog_status()` returns `{success, enabled, installed, built_at,
  sources: {name: {count, updated_at}}, last_check, last_error, checking}`.
- `check_catalog_now()` starts a forced background check and returns the status
  plus `started`; it fails with an error when the catalog is turned off.
- `get_settings()` includes `catalog_enabled`; `save_settings({catalog_enabled})`
  stores `"1"`/`"0"`. Turning it off deletes `catalog.db` and `catalog.json`;
  turning it on starts a check. The setting is local and not part of sync or
  JSON export.
- After a new snapshot installs, and once per start when one is installed,
  `_fill_ratings_from_catalog` fills F95 ratings and review counts from the
  catalog (reading `f95_thread_details.rating_count` when the snapshot includes
  it). It is guarded by the device-local setting `catalog_rating_fill_sha`, so
  each snapshot is used once.

### Discover index

`core/catalog_discover.py` builds `<data dir>/discover-index.db`, a
device-local index for the Discover page with one row per catalog game group
(`game_groups`; one row per entry when a snapshot has no groups). Rows hold the
card fields already resolved (title, developer, newest version, a cover the
window may load, sites, tags, status, engine, weighted F95 rating, release and
update times) and a normalized `search_text`. `tags` holds the tag list and
`entry_ids` every identity of every entry, for the library markers.
`Api.discover_index` (`DiscoverIndex`) builds it first in
`_on_catalog_installed`, on the catalog thread, when the file is missing, has an
older layout (`meta.format`) or was built from another snapshot
(`meta.catalog_sha256`). It writes a temp file next to the index and uses
`os.replace`, so a failed build keeps the old index. Turning the catalog off
deletes the index; so does a start with the catalog off or not installed.
Library export and sync never include it.

`core/api_mixins/discover.py` (`DiscoverMixin`, a `LibraryMixin` subclass) is
the bridge for the Discover page. Every method except `get_discover_status`
returns `{success: False, error_code: "catalog_off" | "not_ready"}` while the
catalog is off or the index is not built.

- `get_discover_status()` returns `{enabled, installed, ready, building, error,
  built_at}`.
- `get_discover_filters()` returns the tag list (`key`, `name`, `count`), the
  engines and the statuses with game counts.
- `search_discover(params)` validates the query with `parse_query` (unknown
  values are dropped; pages hold at most 120 games) and returns `{games, total,
  next_offset}`. Each query reads the library identities (F95 and LC thread
  IDs, `game_links`) and joins them with `entry_ids`, so the `library` marker
  (`installed` or `wishlisted`) and "Hide my games" always follow the current
  library.
- `get_discover_game(key)` adds the preview details from the catalog: the
  entries with their page URLs and LC tier, the overview (F95, else LC), the
  original title, aliases, languages, DLsite genres, and `download:
  {available, reason}` ("Needs LC Plus" for an LC-only Premium thread without
  LC Plus).
- `get_discover_screenshots(key)` returns the F95 catalog screenshots (preview
  and full-size hosts), else the LC ones as local `lc-images` addresses from
  `LcImageKeys` (LC images of a game that also has an F95 thread need "Use
  LewdCorner").
- `add_discover_game(key)` returns `{game_id, created}`. A game that already
  matches a library game returns that game, except a match by store links
  alone, which gets the F95 thread attached. Otherwise it calls
  `add_game(..., fetch_metadata=False)` with an empty executable and the
  catalog fields, the store links of every entry, and the LC thread under the
  library's LC rules ("Use LewdCorner", LC Plus for Premium, not yet claimed;
  an LC-only game always keeps its thread). No F95 request is sent: the
  rating and review count, the catalog fills and the Completed state come
  from the catalog.
- `discard_discover_game(game_id)` deletes a game only when Discover created
  it in this app session (`_discover_created`), it is still wishlisted and it
  has no download-queue job; otherwise it returns `{removed: false}`.

The publisher stores the F95 review count in the optional
`f95_thread_details.rating_count` snapshot column. A positive number is a
count collected from the thread page. Zero means the page explicitly reports
no reviews. NULL means the count is unknown. Older snapshots may omit the
column. The paced thread queue backfills counts for threads read before the
column existed; the `rating_count_attempted` flag keeps a thread from
entering that backfill again. A failed read keeps the stored count.

The feed supplies the average rating independently of the count. An available
count comes from the last successful thread-page read. After backfill, the thread is reread when its feed timestamp advances. Review
activity alone can leave a count stale even while the feed rating changes.

## Library sync and encrypted backups

`core/library_sync.py` contains `SyncManager`, `FolderLocation`, `DropboxLocation`, and `GoogleDriveLocation`. All locations expose revision/read/write methods. Sync shares metadata, user state, and general settings using `wlib.library_migration` v1 plus a UTC `sync.modified_at` and hostname `sync.device`. Machine paths, launch settings, and local cover files are excluded. When only one side changed since the last sync, that side replaces the other for the whole library. When both changed, or when the sync file would remove most of the local games (an empty file from a device whose folder sync had not delivered the real one yet), `_run_once` stops in `needs_choice` with `choice_reason` `conflict` or `removal` and waits for Use sync file, Use this machine or Merge once; push-only runs and the exit push never resolve it. A first sync on an empty library with no sync file pushes nothing. A new revision whose `sync.modified_at` equals `sync_last_synced_at` (a sync tool rewrote the file) counts as unchanged. Simultaneous use from several machines is unsupported.

First connection pauses at `needs_choice` if both libraries contain games. `use-remote` mirrors the file including deletions, `use-local` replaces the file, and `merge-once` imports without deletions then uploads. A choice (on the first connection or later) applies only to the sync file revision that asked for it: if the file changed, the run continues as if no choice was given, and when it asks again `last_error` says to choose again. Sync uses conservative F95 thread, exact store-link, then title/developer matching, with unique-title matching for manual games without a developer; ambiguous candidates are preserved and reported. Before a pull or a sync merge changes the library, every backup section is saved to `<data dir>/sync/snapshots/<UTC time>.json` (the last five are kept, pruned only after the change commits; a failed pull deletes its snapshot, so retries cannot push older ones out; a pre-existing `sync/last-local.json` joins the list). `list_sync_snapshots()` lists them and `restore_sync_snapshot(name)` mirrors one back, including its executable paths and launch options, saving the current library first (even an empty one, so the restore can be undone; a pull into an empty library saves nothing); the next sync uploads the result. The Sync panel offers this as "Restore an earlier library". Folder sync also removes `wlib-library.json.tmp.*` files older than an hour that a killed writer left in the sync folder. Local edits during downloads cause re-evaluation; uploads retain any edits made after the payload was captured. Before each upload, `sync_pending_push` records the pushed change time and device; if the upload worked but its reply was lost (a timeout), the next run (also the first one) sees its own file and records it as synced instead of asking "both sides changed" or which library to keep. File uploads and downloads wait 60 seconds, other provider requests 8. A sync file that is not valid JSON (for example half-written by a cloud client) retries with the normal backoff instead of stopping automatic sync. On import, a blank setting means "never set there": it keeps the local value (including library folders), and only a mirror (sync pull or snapshot restore) stores the blank, which the app reads as the default (a blank yes/no setting is never turned into "false").

Bridge methods: `get_sync_status`, `set_sync_folder(path)`, `connect_dropbox`, `connect_gdrive`, `disconnect_sync`, `sync_now`, `pause_sync`, `resume_sync`, `resolve_sync_choice(choice)`, `set_sync_passphrase(passphrase | null)`, and `unlock_sync(passphrase)`. Failures include `error_code`. Runs execute in background threads and status is polled by the UI. Startup checks both sides; the 60-second watcher (`_watch_tick()`) pushes after 30 seconds without local edits and runs a full sync (pull included) every 5 minutes. A failed run is retried after 1, 2, 4 … up to 30 minutes, or after the provider's `Retry-After`; errors only the user can fix (rejected sign-in, full storage) are not retried; a broken sync file is retried, since a cloud client may still be writing it. Being offline or a 5xx is `location_unavailable`, a 429 is `rate_limited`, and a full Dropbox or Drive is `dropbox_full`/`gdrive_full`; only a refused grant is `*_auth_failed`. `_error` sets the state to `offline` (not `error`) for `location_unavailable`: the location cannot be reached and wLib retries on its own. The watcher starts no push while the state is `error` or `offline`; for an offline folder location it checks `is_dir()` on each tick and starts a full run at once when the folder is back, instead of waiting for the backoff. Offline Dropbox and Google Drive wait for the backoff. Signing in again to the connected account keeps the sync state and encryption key. A failed or cancelled sign-in does not change the active connection: status reports it in `signin_error` (in memory only, cleared by the next sign-in or location change), not in `last_error` or `error_code`. Exit allows a final push up to 10 seconds. `pause_sync` sets the device-local setting `sync_paused` (the `sync_` prefix keeps it out of backups and the sync file); it does not take the run lock, so a run in progress finishes. While paused, `start_run()` (startup, Sync now, choices, passphrase, set folder, snapshot restore), the watcher and the exit push start nothing, and `status()` reports `state: "paused"` (unless a run is still `syncing`) plus `paused: true`. The pause stays after a restart. `resume_sync` clears it, resets the backoff and starts a full run at once. Disconnect and connecting a different location clear the pause; re-selecting the same folder keeps it. Push-only runs do not pull remote changes; pulls emit `wlib-refresh-library`. The main window polls sync status and marks the Sync nav item (and shows a toast once) while sync needs attention; `offline` and `paused` get no marker and no toast.

Folder writes check mtime/size revisions, preserve `.bak`, write `.tmp`, and replace atomically. A missing folder is unavailable and is never created. `FolderLocation` turns a raw `OSError` into a readable `SyncError`: `ENOSPC`/`EDQUOT` is `folder_full`, `EACCES`/`EPERM`/`EROFS` is `folder_not_writable` (both stay `error` and are retried with the backoff), and every other errno, such as `ENOTCONN`, `EIO`, `ESTALE` or `EHOSTDOWN` from a disconnected network or FUSE mount, is `location_unavailable` with "The sync folder is unavailable. wLib will try again." Dropbox uses urllib with the configured SSL certificates and app-relative `/wlib-library.json` (visible as `/Apps/wLib/wlib-library.json`). Uploads use update/add with strict revision conflicts; conflict responses trigger re-evaluation. Access tokens stay in memory and refresh on expiry or a 401.

Dropbox uses OAuth PKCE S256 with offline access and a ten-minute state expiry. `GET /dropbox/callback` on the existing server forwards code/state to `complete_dropbox_callback` and returns a static, uncached completion page. Extension origin restrictions remain unchanged. Connect is disabled when port 8183 is unavailable. Configure the exact redirect `http://127.0.0.1:8183/dropbox/callback` and scopes `files.content.read`, `files.content.write`, `files.metadata.read`, and `account_info.read` (display name) in the app console. No app secret is shipped. Disconnect attempts token revocation and clears local credentials even if offline.

Google Drive reuses the PKCE plumbing (`_pkce`, `_token_request`) and the pending sign-in tags its provider, so a Dropbox callback cannot complete a Google sign-in. It requests only the `https://www.googleapis.com/auth/drive.appdata` scope with `access_type=offline` and `prompt=consent`, so wLib sees only its own hidden app data folder, never other Drive files. `GET /gdrive/callback` (redirect `http://127.0.0.1:8183/gdrive/callback`, a Desktop OAuth client) is routed through the same handler as the Dropbox callback via `OAUTH_CALLBACKS` in `core/extension_server.py`; bridge methods are `connect_gdrive` and `complete_gdrive_callback`. Settings keys are `sync_gdrive_refresh_token` and `sync_gdrive_account` (the Google email). `GoogleDriveLocation` finds `wlib-library.json` by name in `appDataFolder` on every revision check (earliest `createdTime` wins when duplicates exist), uses the file's `md5Checksum` as the revision (Drive's `version` keeps rising after an upload, so it can't be compared with the value from the upload response), and keeps the file ID in memory only. Drive v3 has no conditional upload (no ETag or `If-Match` on `files.update`): `write` compares the checksum, then creates (multipart) or updates (media `PATCH`). After an update it reads `revisions.list` and checks that the revision just before its own upload (the `headRevisionId` from the reply) holds the expected checksum. If another device uploaded in between, `write` marks that replaced revision `keepForever` (Drive serves an earlier revision's content only with this mark), downloads it, uploads it again, removes the mark and raises `SyncConflict`, so the retry reads the other device's file and asks for a library choice; the other device keeps its checksum as synced. If the mark, the download or the upload fails, `write` raises `DriveRestoreFailed` (code `gdrive_restore_failed`, or the cause's `rate_limited` / `gdrive_auth_failed` code), the revision keeps its mark, and `_push` clears `sync_pending_push` and saves the revision and its own checksum in the device-local `sync_gdrive_replaced` setting (one record at most; a newer one releases the older mark). Each run first calls `restore_replaced`: while the file is still that upload (checked again after the download, so a third device's upload in between is not replaced) it puts the revision back and removes the mark, so the normal run then asks for a library choice against the other device's content; after a later upload it only removes the mark. A failed retry keeps the record, and after `RESTORE_ATTEMPTS` (5) failed runs sync goes on without it; a run that fails because the device is offline, rate limited or signed out (`RESTORE_WAIT_ERRORS`) uses up no attempt (the mark stays, so Drive does not purge the revision). If a third upload already followed, or one lands during the download, it releases the mark and raises `SyncConflict`. If the revision list cannot be read, the upload is kept unchecked. Putting the replaced content back is itself not atomic, and two devices that create the file at the same moment are not checked. Replaced versions stay in Drive's revision history, which is not reachable from the Drive web UI for app data files. Reconnecting does not revoke the previous token, because Google revokes the whole grant and that would invalidate the new token too; Disconnect revokes it and leaves the sync file in Drive.

The Google client ID is a public constant (`GDRIVE_CLIENT_ID`). Desktop clients must still send a client secret, which Google does not treat as confidential for installed apps but which stays out of the repository. `_gdrive_client_secret()` reads `WLIB_GDRIVE_CLIENT_SECRET` first, then the gitignored `core/_gdrive_secret.py` written by the build scripts (see `docs/build.md`). Without it `gdrive_available` is false and `gdrive_unavailable_reason` says why, as it does when port 8183 is unavailable. Folder and Dropbox sync are unaffected.

`core/library_backup.py` encrypts the complete JSON document with scrypt (N=131072, r=8, p=1) and AES-256-GCM from `cryptography`. The v1 `wlib.encrypted` envelope authenticates its header and uses a fresh nonce. Manual exports use fresh salts; sync stores only a derived key and salt locally. Unknown keys/salts pause at `needs_passphrase`. Disabling encryption clears the key and marks the next write for plaintext. Backup load/inspect/import/write accept optional passphrases; errors include `passphrase_required`, `decrypt_failed`, and `unsupported_format_version`. Sync settings and credentials remain outside backup allowlists.

The core strength of wLib relies on its native Python backend, divided primarily into `main.py` and modularized controllers in the `core/` package. The supported development and CI target for backend work is Python 3.12.

## Bootstrapping in `main.py`
`main.py` acts as the primary orchestrator. Upon launch, it executes these sequential steps:

1. **SSL Certificate Configuration**: Configures SSL certificates from bundled certifi or system paths for secure scraping (`configure_ssl_certificates()`).
2. **Single-Instance Lock**. Holds `.wlib-instance.lock` in the data directory through shutdown, so a second launch exits after attempting to focus the running window even when the extension server on `127.0.0.1:8183` cannot respond.
3. **Data folder check**: `main.py` checks that the data folder can be written. If not, it shows the reason through zenity, kdialog or notify-send (and stderr) and exits with code 1.
4. **App Log**: Calls `setup_app_log()` so `<data dir>/logs/wlib.log` captures console output, Python logging, and uncaught exceptions before the rest of startup runs.
5. **Qt Runtime and WebView Cache**: Detects the Linux session type (X11/Wayland) and configures Qt platform plugins; on Windows, leaves native platform selection to Qt unless explicitly overridden (`configure_qt_runtime_environment()`). Both platforms start PyWebView with `gui="qt"`. Packaged runs refresh the WebView cache when the app version or bundled UI changes.
6. **WebView Load and Startup Diagnostics**: Imports `pywebview`, then records the Qt and renderer startup snapshot.
7. **API and Database Initialization**: Constructs `core.api.Api`, which calls `core.database.init_db()` to create/migrate the SQLite schema, prunes orphan attachment folders (PDF, TXT, MD), and creates the sync, scraper, and launcher services.
8. **Extension Sync**: Copies bundled extension assets into the platform user-data directory when files are missing or the bundled manifest version changed.
9. **Window and Background Services**: Creates the PyWebView window, starts legacy browser-data cleanup and the extension server daemon thread, and starts the library sync watcher. Once the window exists, SIGTERM, SIGHUP and SIGINT close it (a pipe set with `signal.set_wakeup_fd` wakes a watcher thread, since Python signal handlers do not run inside the Qt loop), so playtime is saved and the last sync runs; a repeat after five seconds exits at once. `wlib.sh` and the packaged launcher run the app in the background and forward SIGTERM/SIGHUP to it.
10. **UI Loop**: Enters the blocking UI loop, then allows a final sync push on exit.

`main.py --smoke-test` validates imports, database initialization, and bundled assets without opening the UI or downloading external content.

### Renderer Diagnostics System

`main.py` logs Qt and WebGL renderer details under the resolved data directory on both platforms: `~/.local/share/wLib/renderer-diagnostics.log` on Linux or `%LOCALAPPDATA%\wLib\renderer-diagnostics.log` on Windows. The Linux release launcher supplies the GPU probe and crash-guard context described below; Windows uses Qt's native selection.

- **GPU Detection**: Probes GPU capabilities using `glxinfo`, `/sys/class/drm/`, and environment variables
- **Crash Guard**: Implements `<data dir>/.gpu_crash_guard` to auto-fallback to software rendering after GPU crashes
- **Diagnostic Logging**: Logs Qt backend selection, GPU detection reason, renderer details, and WebGL probe results to `<data dir>/renderer-diagnostics.log`
- **Browser Renderer Probe**: Executes WebGL detector scripts in the PyWebView to capture the browser's GPU renderer information
- **AppImage Mirroring**: AppImage launches mirror diagnostic context to `<data dir>/appimage-launch.log`

## Core Modules

### `core/host_platform.py` (Host Paths and Capabilities)

Centralizes Linux/Windows detection, data/cache/extension paths, and platform capabilities. `Api.get_platform_capabilities()` exposes these through `getPlatformCapabilities()` in the frontend bridge. Linux-only runtime installers return `success: false` with `code: "unsupported_platform"` before starting downloads or subprocesses on Windows. Windows file/folder and HTML opening uses system associations. See [Platform Paths](architecture.md#platform-paths) for defaults and environment overrides.

`Api.get_install_status(prefix_path, proton_path)` reports `success`, `deps`/`rtps` progress payloads (`running`, `done`, `total`, `current`, `error`), and the derived `dlls_installed`/`rtps_installed` flags for the resolved prefix. On hosts without runtime installers it keeps that same shape and reports `success: false` with `code: "unsupported_platform"`, so the polling dialog can read either response the same way.

`is_flatpak()`, `host_which()`, and `host_command()` keep game processes and external tools on the host. Inside a Flatpak sandbox, commands are wrapped in `flatpak-spawn --host` (with `--watch-bus`, optional working directory and environment overrides, and process-group supervision for tracked launches); sandbox-only variables such as `LD_LIBRARY_PATH`, `QT_*`, and `FLATPAK_*` are not forwarded. Runner discovery, archive tools, runtime installers, notifications, and game launches reuse these helpers.

On Linux, `open_on_host()` opens folders and URLs for the main app and the web player. It tries `xdg-open`, `gio open`, `kde-open5`, `kde-open` and `gnome-open` in turn. An opener counts as started when it exits with code 0, or when it is still running after `OPENER_START_WAIT_SECONDS` (2 s). When it exits with another code first, the next opener runs. If every opener fails, the API returns `success: false` with each exit code. The web player runs this on a worker thread (`open_in_background()`) and shows its failure message through `gui_thread_relay()`.

`host_open_env()` is the environment for host openers, the `zenity`/`kdialog` file pickers and the archive tools. It starts from `host_tool_env()` (no AppImage variables, `LD_LIBRARY_PATH` from `LD_LIBRARY_PATH_ORIG`). It also removes the `QT_PLUGIN_PATH` and `QML2_IMPORT_PATH` entries inside `sys._MEIPASS` or `$APPDIR`, every name in `WLIB_OWNED_ENV`, `WLIB_QPA_PLATFORM`, and an empty `QT_STYLE_OVERRIDE`. The PyInstaller PyQt6 hook points `QT_PLUGIN_PATH` at the bundled Qt. A system Qt program with the same Qt minor version (for example `kde-open` on Fedora 44) would load a bundled platform plugin and abort. `WLIB_OWNED_ENV` lists the comma-separated variables that wLib set and the user did not: `QT_QPA_PLATFORM` from `configure_qt_runtime_environment()`, `QT_QUICK_BACKEND` from the launcher GPU check, and `QTWEBENGINE_DISABLE_SANDBOX` for a sandboxed web player. `mark_wlib_owned()` adds a name. Values the user set stay. Game launches use `without_packaged_runtime_env()` in `core/launcher.py`, which drops the marker too.

Flatpak host lookup uses `sh -lc` to load the login PATH, then appends `~/.local/bin`, `~/.nix-profile/bin`, `/nix/var/nix/profiles/default/bin`, `/home/linuxbrew/.linuxbrew/bin` and `/run/current-system/sw/bin`. A lookup that exceeds ten seconds counts as not found. The bundled archive extractor is the exception to host execution: `/app/bin/7zz` runs directly inside the sandbox.

### `core/api.py` and `core/api_mixins/` (The API Bridge)
The `Api` class acts as the single point of entry for the Vue frontend. PyWebView lists each public method (no leading underscore, e.g. `get_games`, `launch_game`) as a Promise on the `window.pywebview.api` object, except the names that `core/bridge_exposure.py` hides (see below).
- **Layout**: `core/api.py` holds only the `APP_VERSION` and `normalize_version` re-exports and `class Api`, which combines the feature mixins in `core/api_mixins/`: `library`, `sync`, `extension`, `launch`, `updates`, `game_tools`, `runtimes`, `rpgm_runtime`, `downloads`, `saves`, `settings` and `web_media`. Each mixin subclasses `ApiBase` (`core/api_mixins/base.py`), which owns `__init__`, all shared instance state, and each method that two or more mixins use. Shared TypedDicts and Protocols live in `core/api_mixins/types.py`. Put a new method in the mixin for its feature; if a second mixin needs it, move it to `ApiBase`. A mixin never calls a method of another mixin. A name may be defined in only one class of `Api.__mro__` (`tests/test_js_api_surface.py` checks this). The `APP_VERSION = "..."` line lives in `core/app_version.py` (release and build scripts read it there); mixins import it from that module, never from `core.api`, so there is no import cycle.
- **Test patches**: a test that replaces a host or path function (`is_linux`, `host_which`, ...) for `Api` uses `patch_api_name(monkeypatch, name, value)` from `tests/api_patching.py`, which replaces the name in every `core.api_mixins` module that imports it.
- **Bridge listing**: PyWebView also walks into public helper objects and lists their methods as nested names. `core/bridge_exposure.py` keeps names off the listing: `hide_from_js()` flags the helper objects (`scraper`, `launcher`, `library_sync`, `cover_cache`, `cover_cards`, `catalog`, `steam_sync` and `window`), and `@python_only` flags methods that only Python calls (for example `set_window`, `reserve_runner_launch` and the OAuth `complete_*_callback` methods). Both set PyWebView's `_serializable = False` flag. `tests/test_js_api_surface.py` pins the listing in `tests/fixtures/js_api_surface.json` and checks that it equals the names `ui/src/services/api.ts` calls; rewrite the fixture on purpose with `WLIB_UPDATE_SNAPSHOT=1 pytest tests/test_js_api_surface.py`. Hidden means not listed, not blocked: PyWebView resolves a called name with `getattr` and has no allow list, so page JavaScript can still call a hidden name.
- **Concurrency**: UI calls are technically asynchronous on the JS side but block the pywebview worker pool on the Python side. The `Api` class heavily uses background thread spawning (`threading.Thread`) for long tasks (like downloading updates or mass-scraping metadata) so the UI doesn't freeze.
- **Event Emitter**: Contains wrapper helpers to dispatch Global UI Events back to Vue using `webview.evaluate_js()`.
- **Extension Sync Metadata**: Tracks whether startup extension synchronization actually updated the installed browser files so the frontend can show a toast prompting the user to reload the addon.
- **Launch Mode Contract**: Carries each game's `launch_mode` through add, update, list, and launch calls. Missing or invalid values normalize to `auto`; supported values are `auto`, `native`, `wine_proton`, `rpgmaker_linux`, and Linux-only `custom`. Add and update calls also accept `command_line_args` and `block_network` (the per-game No internet preference).
- **Launch Target Contract**: Exposes CRUD and reordering methods for additional game launch targets. `get_games()` returns each game's extra `launch_targets`, while the canonical default executable remains `games.exe_path`.
- **Store Links and Local Covers**: `add_game` accepts `links: [{source, id, url}]`; `get_games()` returns normalized `links`, and the extension can replace F95-post links through `POST /api/thread-links`. `choose_game_cover`, `set_game_cover_file`, and `clear_game_cover` manage device-local cover files; game payloads include `cover_local_url` while the extension server is bound. `get_cover_cache_status()` and `purge_cover_cache()` report and flush the remote cover cache.
- **Finished Version Contract**: `update_game` accepts a free-text `finished_version` next to `version`; the value is trimmed and empty means not finished. When a call moves `play_status` to `Completed` from another status without sending `finished_version`, the backend fills it with the call's `version` — or the stored `version` when none was sent — in the same write. Re-saving `Completed` and leaving `Completed` both keep the stored value, and an explicit `finished_version` in the same call wins. The success response includes `finished_version` only when the backend filled it; unrelated edits return just `{"success": True}`. Version-only updates ("Mark updated"), archive installs, and metadata refreshes never touch the field.
- **Library Migration Contract**: Exposes `export_library_backup`, `inspect_library_backup`, and `import_library_backup` for one-file JSON migration. Import uses an inspect-before-write flow and backup-wins field merges for selected sections.
- **External Library Import Contract**: Exposes `detect_external_library(source)`, `inspect_external_library(source, path)`, `import_external_library(source, path, options)`, and `browse_external_library_file(source, start_path)` for bringing a library in from F95Checker, Atlas, XLibrary, f69, Playnite, or Game-List (`source` is `"f95checker"`, `"atlas"`, `"xlibrary"`, `"f69"`, `"playnite"`, or `"gamelist"`). Detection reports the found path plus the default locations checked; the file picker falls back to per-source filters when nothing is found. For Game-List, choose `Games.fic` manually and keep the optional `Games.mmo` beside it. Inspect previews new/matched/ambiguous counts plus skipped games without an F95 thread, a qualifying store link (DLsite, Fanza, VNDB or Ryuugames), or a usable executable, dropped cross-OS executable paths, optional local-cover copies, and the source schema version. XLibrary and Atlas use the first host-compatible alternate as the default executable when the source default has no host-compatible path. Both the preview counters and import result include `skipped_unreadable`, which counts unreadable or incomplete Game-List records and defaults to zero. Import accepts `sections` (`user_state`, `executable_paths`, `launch_targets`, `covers`; game identity and metadata always apply to matches) and `merge_mode` (`"overwrite"` or `"fill_missing"`, defaulting to overwrite; fill-missing only sets fields that are empty locally and keeps existing launch targets). Results include `created_ids`/`updated_ids`, and imports that touch games with F95 URLs start `check_all_updates(game_ids=...)`, returning `metadata_check` as `"started"`, `"busy"`, or `"none"`. Failures return `{"success": False, "error": ...}`. The readers live in `core/external_import.py` (`read_external_library`, `locate_external_library`); SQLite sources are read from a temporary copy opened read-only so the source app can keep running.
- **F95 Account Import**: `start_f95_account_read()`, `get_f95_account_read_status()`, `cancel_f95_account_read()` and `import_f95_account_lists(read_id)` read the signed-in user's F95 Watched games and Bookmarked games lists through the paired extension only (no F95 login or cookies in wLib). `core/f95_lists.py` walks Watched games, then Bookmarks, sorted by title, one page per request in the shared F95 slot (`scraper.run_paced_f95_request`). A list stops at a page with no rows, a page of only repeated rows, or page 200. Rows are read only inside `.p-body-pageContent` (thread ID from `js-threadListItem-<id>`, then `uix-href`, then the `data-tp-primary` link). The read runs in a background thread (`AccountReader`); its preview (counts per list, total, new and existing, matched by thread with `find_matching_game_row`) is kept in memory for 2 hours or until the next read. Import applies that preview in one SQLite transaction: new games are inserted wishlisted (empty executable) with catalog values first (`game_lookup.f95_thread_entries`) or the row title split; every list game gets "Watched on F95" and/or "Bookmarked on F95". Existing games only get the tags; a game with no F95 tag baseline and unedited tags first gets its current tags as `f95_tags`, so "Refresh F95 info" keeps the list tags. A new game without catalog tags gets an empty baseline (`f95_tags = ""`); the update check's metadata backfill then puts the thread's tags in front of the list tags and records them as the baseline. The first import colors the two tags Orange and Purple when they have no color, then sets the general setting `f95_list_tag_colors_seeded`, so a color the user clears stays cleared. A failed Import (database error) rolls back and keeps the preview, so Import can be retried without reading F95 again. After Import, `check_all_updates` runs for the added games only. Errors return `{"success": False, "error", "error_code"}` with `no_extension`, `extension_outdated`, `login_required`, `blocked`, `not_a_list`, `rate_limited`, `timeout`, `fetch_failed`, `cancelled`, `busy`, `not_running`, `not_found`, `expired`, `empty` or `import_failed`.
- **Folder Import**: `inspect_game_path(exe_path)` guesses a title, version, and engine for the Add Game form; `scan_games_folder(folder)` walks subfolders (symlinked game folders too), picks a launch file, lists each real executable once (a game folder and a symlink to it give one row, through the folder itself), and marks entries already in the library with `in_library`. The Import Folder dialog adds selected rows through one `add_game` call per game and refreshes the library once. Guesses come from folder names and files, so the frontend lets the user review and edit them after import.
- **Runtime Setup (Linux)**: `install_rpgmaker_dependencies(prefix_path, proton_path)` runs Winetricks verbs for common DirectX/VC++/.NET/font dependencies; `install_rpgmaker_rtp(prefix_path, proton_path, game_id)` downloads the official RTP archives and runs their setup silently. With a `game_id`, the RTP installer and `open_wine_prefix_tool()` use the prefix that game launches in: a `WINEPREFIX=` in its saved launch arguments (with `%command%` or Custom Command, read by `launcher.launch_env_overrides()`) wins over the prefix fields. Proton targets use umu and the selected build's bundled Winetricks; plain Wine targets use host tools. Both start background threads, refuse concurrent installs, and report through `get_install_status()`. `get_system_deps_command()` detects the distro package manager and returns the command for 32-bit GStreamer/multimedia libraries. `download_proton_ge()` and `get_proton_download_status()` cover the checksum-verified GE-Proton download, and `is_cheat_engine_installed()`/`download_cheat_engine()` cover the pinned Lunar Engine archive. The Windows host rejects these Linux-only helpers before doing any work.
- **umu management (Linux)**: `get_umu_status()` reports the host or wLib copy and host Python availability. `download_umu()` starts the verified upstream download; `get_umu_download_status()` reports its progress and errors. `prepare_umu_runtime()` starts preparation for the global runner and default prefix; `get_umu_runtime_status()` reports the selected runtime, readiness, progress and failure class, and `cancel_umu_runtime_prepare()` requests cancellation. These methods reject non-Linux hosts.
- **Process Control**: `get_running_games()` returns a list of game IDs; `stop_game(game_id)` requests termination and returns a success/error payload. Duplicate tracked launches return `already_running`; stopping an untracked game returns `not_running`, and stopping one whose process is still starting (e.g. behind a UAC prompt) returns `starting`.
- **Custom Statuses**: `get_settings()` returns `custom_play_statuses` as a list. `save_settings()` validates trimmed names (1–40 characters, no case-insensitive duplicates, canonical clashes, or legacy aliases such as `Replaying`); removing a name resets games using it to `Not Started` in the same transaction as the list update.
- **Collections**: `get_collections()` returns the ordered collection list; `create_collection(name, game_id=None)`, `rename_collection(old, new)`, `delete_collection(name)`, `reorder_collections(names)`, and `set_game_collections(game_id, names)` each rewrite the setting and affected game memberships in one transaction and return `{"success": True, "collections": [...]}`, or `{"success": False, "error": ...}` on refusal (invalid or duplicate names, unknown collection or game). `get_games()` returns each game's `collections` as a `list[str]` filtered against the current collection list. Names are 1–40 characters, unique ignoring case, and `All` is reserved.
- **Filter Presets**: `get_settings()` returns `library_filter_presets` (a list of `{name, filterCollection, filterStatuses, filterInstallState, filterSources, filterEngines, filterTags, filterExcludedSources, filterExcludedEngines, filterExcludedTags, sortBy, sortDir}` objects); `save_library_filter_presets(presets)` validates the whole list (1–40 character names, unique ignoring case) and writes it as one JSON setting. The getter drops unreadable entries and case-insensitive duplicates so a malformed sync payload can't break the settings payload.
- **Path Checks**: `check_path(path, kind)` reports `{ok, reason}` for a typed path without blocking anything: `file` wants an existing file, `dir` an existing folder, `parent` an existing folder for a file wLib will create, and `runner` an existing file when the value has path separators or a command found on PATH otherwise. `~` is expanded like the launch paths; an unknown kind returns `{"success": False, "error": ...}`.
- **File Timestamps**: `get_executable_modified_time(exe_path)` returns `{success, modified_at}` from the executable's filesystem mtime, or `modified_at: None` with an error for a missing path. Game Detail uses it for the Overview footer's **Exe modified** line; the adjacent **Thread updated** line uses `thread_main_post_last_edit_at`/`thread_main_post_checked_at`.
- **URM**: `urm_rpa_path` stores a user-supplied archive path. `browse_urm_file()` selects `.rpa` files. `get_urm_status(game_id)` returns `success`, `renpy`, `installed`, and `source_configured`. `set_urm_installed(game_id, installed)` (controls live in the Tools tab) detects `renpy/` plus `game/` beside the stored executable and installs/removes `game/0x52_URM.rpa`. It goes through the same `_tool_run` guard as the other tools, so it is refused while the game runs, is updated, moved or uninstalled, or another tool is busy with it. Installs replace the destination only after a successful copy; filesystem errors return `success: false`. No download is performed.
- **Runner Discovery**: `get_available_runners()` lists system Wine and wLib Proton first, then Steam and Lutris, sorted within each source and deduplicated by real path. Steam roots: `~/.steam/root`, `~/.steam/steam`, `~/.local/share/Steam`, `~/.var/app/com.valvesoftware.Steam/data/Steam`, and `~/.var/app/com.valvesoftware.Steam/.local/share/Steam`; scans `compatibilitytools.d/*/proton` and `steamapps/common/Proton*/proton`. Lutris scans `*/bin/wine` under `~/.local/share/lutris/runners/wine` and `~/.var/app/net.lutris.Lutris/data/lutris/runners/wine`. Windows returns an empty list.
- **Archive Install Contract**: `browse_archive_file()` picks `.zip`/`.7z`/`.rar` files and tar archives (`.tar`, `.tar.gz`, `.tgz`, `.tar.bz2`, `.tbz2`, `.tbz`, `.tar.xz`, `.txz`). `inspect_archive(path, game_id=None, target_id=None, library_folder=None)` is read-only: guessed title/version, the stored engine for updates, destination preview, `engine_pending`, tool availability, and the old-folder guard. `preview_install_destination({title, version, creator, engine, game_id?, library_folder?})` recomputes `{destination, engine_pending}` without filesystem writes; the flag means the pattern contains an unresolved `{engine}`. `lookup_thread_details(url)` uses the paced scraper and extension fallback, then `core.f95zone.split_thread_title()` to return `{success, title, version, creator, engine, cover_image, tags}`; invalid URLs and lookup failures return `{success: False, error}`. `install_archive(options)` blocks while pywebview runs it on its own thread; the dialog polls `get_archive_install_status()` (guarded by `_status_lock`). Updates for a running game are refused (`game_running`); a thread URL that belongs to another game returns `duplicate_url` with that `game_id`. `install_archive` accepts `engine`, `cover_image`, `tags`, and `rating`; cover/tags/rating apply to new games only. New installs with a URL get the same background metadata fetch as `add_game`, backfilling missing fields. Success fires `wlib-refresh-library`. Failures return `{"success": False, "error": ...}`.
- **Download Offers**: `find_download_offers()` lists the Downloads folder without watching it; `dismiss_download_offer(key)` persists `path|size|mtime` keys (capped at 200). A missing folder reads as an empty list, never an error.
- **Game Notes and Attachments**: notes live in `games.progress` as markdown; `note_links` stores ordered `{url, label}` objects. URLs must be absolute HTTP(S), at most 2048 characters, with exact duplicates removed; labels are trimmed and capped at 200 characters. ### `core/archive_install.py` (Install From Archive)
Pure filesystem logic behind the install flow; `core/api_mixins/downloads.py` stays a thin wrapper.
- **Formats**: `.zip` extracts with the stdlib (`zipfile`) including per-entry path validation and Unix modes from `external_attr`. `.7z`/`.rar` use the first available system tool (`7zz`/`7z`/`7za`, `bsdtar`, `unrar` for rar; plus `%ProgramFiles%\7-Zip` on Windows) with a listing-based traversal pre-check and a post-extraction symlink escape check. Without a tool the error names 7-Zip. **Passwords**: an optional `archive_password` (from the thread's first post, a queued download, or typed in the install dialog) goes to `zipfile`, 7-Zip and unrar; bsdtar gets it for zip only, so a password-protected `.7z`/`.rar` skips bsdtar and asks for 7-Zip. A missing password fails with `archive_password_required`, a wrong one with `archive_password_wrong`, and the password is removed from error details. Tar archives (`.tar`, `.tar.gz`/`.tgz`, `.tar.bz2`/`.tbz2`/`.tbz`, `.tar.xz`/`.txz`) need no system tool: `extract_tar()` reads them once with the stdlib `tarfile` in stream mode (the compression comes from the content, not the name; gzip, bzip2 and xz go through the stdlib `gzip`/`bz2`/`lzma` readers, which are read to the end so a bad CRC or check fails the install). A member header with a bad checksum or cut off after the first member fails the install too (`_StrictTarInfo`); stdlib `tarfile` would take it as the end of the archive. Each member is checked as it is read (`check_archive_entry_safe()`, a running collision set keyed by where the member lands after symlinks extracted earlier are followed, and by `_windows_name_key` on Windows, no device/FIFO entries, hard links only to an earlier file) and then extracted with the `data` filter, which refuses links out of staging and clears setuid and group/other write bits while keeping the owner execute bit. A missing `bz2`/`lzma` module fails with "This build of wLib cannot read <suffix> archives". `core/archive_formats.py` is the one table of suffixes (longest first) and signatures that the installer, the file-host downloads, the torrent payload pick, the staging cleanup and the file dialog use. No new Python dependencies.
- **Flatpak extractor**: `.7z`/`.rar` prefer the bundled `/app/bin/7zz`, including listings and size checks, so no host extractor is needed. If the bundled binary or archive is missing from the sandbox, or the library folder is not writable there, detection falls back to the host tool order above. Host tools use `host_command()` and the cleaned host environment; the bundled tool inherits the sandbox environment. Other package formats keep system-tool detection.
- **Layout**: `build_destination()` substitutes `{creator}`/`{title}`/`{version}`/`{engine}` in `library_folder_pattern` (default `{creator}/{title}/{version}`), sanitizes each segment (including Windows reserved names), drops empties, and falls back to `{title}`. Staging lives in `<library>/.wlib-staging-*/` so the final move is a rename; stale staging folders are cleaned on the next run, except one that holds a moved torrent download: a `.wlib-staging-*.moved.json` record beside it names the download's folder, and the cleanup puts the download back there (or keeps it when that folder is taken or its torrent folder is gone). While saves are carried into a moved download, the record also holds an `undo` journal (the `.wlib-undo-*` folder name and the relative paths the carry `created` or replaced as `saved`), written before any file changes (a carried save folder is journalled in one write); the cleanup first removes the created files and puts the replaced originals back, and keeps the staging folder when that cannot finish or the journal is not valid. A failed install that cannot take its carried saves out also keeps the staging folder for that cleanup. Because its torrent folder is then missing, `inspect_archive` (when no install runs) and `install_archive` first call `recover_moved_download()`, which puts back only the staging folder whose record names that download, so retrying the same download recovers it. Free space is checked when the uncompressed size is known (a plain `.tar` sums its member headers; a compressed tar has no recorded size, so it needs at least its own file size free); a torrent folder that is not seeding and sits on the library's drive is renamed into staging, so it needs no free space unless the rename fails and it is copied.
- **Zip extraction**: `extract_zip()` inflates and writes members with one worker per usable CPU core (`zip_extract_workers()`, capped at `ZIP_MAX_WORKERS`; at least `NETWORK_IO_WORKERS` on network shares), each worker with its own `ZipFile` handle.
- **Network libraries**: when `/proc/self/mountinfo` puts the library on a network filesystem (`NETWORK_FS_TYPES`: NFS, SMB/CIFS, sshfs, gvfs and similar), 7z, rar and tar extract to local `install-scratch/` and are copied over in parallel, with hard links kept (falling back to direct extraction when local disk is too small, and also when extraction would take local disk below its 1 GiB reserve or fills it; failed installs delete scratch and staging after giving their folders owner access back), and a replaced old version is renamed to `<library>/.wlib-trash-*` and deleted in the background; `sweep_trash()` resumes interrupted deletes on the next install. It deletes only names that wLib makes (`.wlib-trash-` and a 19-digit `time.time_ns()`), so a user folder such as `.wlib-trash-backup` stays. Every zip install sets file modes and execute bits while writing, so there is no separate permissions pass.
- **Ordering**: extract → safety checks → execute bits (Linux `.sh`/ELF via `is_elf`) → flatten a single wrapper folder → detect the engine when `{engine}` is unresolved and recompute the destination and old-folder guard → carry in-folder saves (overwrite) → rename into place → update `games`/`game_launch_targets` → remove the old folder only if asked and allowed → delete the archive last. Engine detection uses the same `game_scan.detect_engine()` rules as folder import; an unknown engine drops the token. A collision at the detected destination removes staging and leaves the library unchanged. Steps before the move roll back (staging removed, `.wlib-old-<ts>` swap restored; a moved torrent download first gets back every file a carried save replaced, kept until then in a hidden `.wlib-undo-*` folder inside staging, and loses the save files the carry added); an in-place update that fails after the move and before the library write restores the swap and keeps the extracted tree as `<destination>.wlib-new-<ts>`; when the chosen launch target was already repointed, it goes back to its old path; a removal failure is reported while the update stands.
- **Progress and cancel**: while extracting, the install reports bytes written to staging about once a second against the archive's unpacked size (`get_archive_install_status()` `done`/`total`); a tar archive instead reports the compressed bytes read against the archive file size, and the dialog shows a percentage. `cancel_archive_install()` works until the new version starts moving into place (`cancellable` in the status; the install checks the cancel again after it publishes `moving into place`, so an accepted cancel is never ignored): zip extraction stops between chunks of a file, tar extraction stops at the next read of the compressed file (also inside one large member), a 7-Zip/unrar/bsdtar process is killed, and staging is removed, so nothing changes (`error_code: install_cancelled`).
- **Multi-part archives**: `volume_set()` recognises `.partN.rar`, `.7z.001`/`.zip.001`/`.rar.001`, `.rar` + `.r00`, and spanned `.zip` + `.z01`. Choosing any part installs from the first; a set with gaps is refused naming the missing parts; names that differ only in letter case or give one part number with different zeros (`part01` and `part1`) are refused, so another set is never extracted or deleted (a chosen file wins only over its own case variants); deleting the archive removes every part. Split and spanned sets need 7-Zip (or unrar for rar sets), never bsdtar. The downloads-folder detector offers a set once, through its first part, after every part is present, none changed in the last 15 seconds, no part is still downloading under a browser's temporary name, and the parts are not all the same size (only the last part of a split is shorter, so equal sizes mean more are coming).
- **Deletion guard**: `can_remove_old_folder()` refuses roots (including a mounted drive's root), home, the library/Downloads folders, folders that contain home, a library folder or the Downloads folder, parents of the new destination, folders holding other games' executables or targets, and stale paths, returning `{removable, reason}` for the dialog.
- **Saves**: the shared in-folder helper (`game/saves`, `www/save`, `save(s)`, `SaveData`, loose `*.sav`/`*.rpgsave`/`*.rmmzsave`/`*.save`; `.dat` excluded) backs both `find_save_files` and save carry-over.
- **Download matching**: `find_download_offers()` keeps top-level archives, skips `.partN.rar` (N>1) and files newer than 15 s, and matches squashed titles only against games with a pending update whose installed version differs from the guess.
- **Settings keys**: `library_folder` (default), `library_folders` (JSON list), `library_folder_pattern`, `downloads_folder`, `download_detection_enabled` (machine-specific paths group in backups), plus local-only `dismissed_download_archives`.

### `core/game_files.py` (Uninstall and Move)
Root detection, the uninstall, the move engine and the move queue. The bridge methods in `core/api_mixins/library.py` stay thin; the Api passes in what the module needs (running and busy games, the saves folder, the "Remove from library" body) as callables.
- **Root detection**: `detect_root()` rebuilds the install folder with `old_install_root()` from `core/archive_install.py` (the library folders and the destination pattern, so an archive wrapper folder below the root is found) and falls back to the executable's folder. `root_source` is `pattern`, `exe_dir` or `override`.
- **Plans**: `plan_uninstall()` and `plan_move()` return, for each game, `root`, `root_source`, the `can_remove_old_folder()` guard result (`removable`, `reason`), `saves_folder`, `saves_inside_root`, `save_files` and `blocked_reason` (running, busy, wishlisted, not found, or on Linux a process whose executable, working folder or a path argument is inside the root: `folder_in_use()` reads `/proc`, so a game that an earlier wLib window started also blocks the plan). A root that is a symbolic link is not removable (the reason names the real folder, which the user can pick instead). When the game has no saves folder but loose save files lie next to the executable (`loose_save_files()`), `saves_folder` is the executable's folder and `save_files` lists those file names. `plan_move()` adds `target`, `same_device`, `size_bytes` (counted on worker threads) and `move_reason` (target exists, destination is or is inside the root, same folder, not enough space on another drive). A root that the user picks comes back in `root_overrides`, and the backend checks it again. Each uninstall and each move job checks its plan again just before it acts.
- **Uninstall**: `run_uninstall()` runs after the frontend's Undo offer. For each game it marks the game as uninstalling (`Api._uninstalling`, checked by `_game_busy_reason()`), backs up the saves when asked (only the `save_files` when the plan lists them, through `backup_saves(..., files=...)`; `NothingToBackUpError` is not a failure; any other backup error keeps the files), renames the root aside (`stage_removal()`: `.wlib-uninstall-<ns>` in the deepest library folder, else beside the root; the trash sweeps skip this name, so a crash here keeps the files), and then clears `exe_path` and the launch targets (`database.clear_game_install()`) or runs the "Remove from library" body. Only after that change is saved does `finish_removal()` start the background delete (library trash, or a `game-file-jobs.json` record outside the library folders). When that start fails (for example the jobs file cannot be written), the uninstall still succeeds, because the library change is saved: the result has `trash: "kept"` and a `warning` that names the kept `.wlib-uninstall-<ns>` folder, and nothing is deleted. When no rename works (a read-only folder, a file in use), the game fails with "The game folder could not be moved to the trash, so nothing was deleted: ..." and the library is not changed. When the library change fails, `undo_removal()` renames the folder back (or names where it was kept) and nothing is deleted. One result per game; the others continue when one fails.
- **Trash**: `trash_root()` renames the root into `.wlib-trash-*` in the deepest library folder (`defer_remove_tree()`), else into `<parent>/.wlib-trash-<ns>` with a record in `<data dir>/game-file-jobs.json`, and deletes it on a daemon thread. When the rename fails, it deletes the root in place on a worker thread. `sweep_leftovers()` runs once in the startup clean-up thread: it sweeps every library folder and every recorded trash and `.wlib-move-*` folder, drops records whose folders are gone, and keeps the record of an offline drive (parent folder missing, or on another device than when it was recorded).
- **Move**: on one device a move is one `os.rename()`, recorded in `game-file-jobs.json` before the rename and dropped after the path update is saved (`finish_interrupted_renames()` in `sweep_leftovers()` finishes the path update at the next start when wLib stopped in between); when the path update fails, the folder is renamed back. Across devices, `ensure_free_space()` runs, then `copy_tree_parallel()` (with its `cancel` event and `on_bytes` progress callback) fills a recorded `<dest>/.wlib-move-<ns>` folder, which is renamed to the final name only when the copy is complete. Then `database.repoint_game_paths()` changes `exe_path`, `cover_image_path`, `custom_prefix`, `save_path_override` and each launch target inside the old root in one transaction, and only then does the old root go to the trash. A cancel or a failure deletes the temporary folder or the new copy, so the game stays at its old place. After each move, `_schedule_steam_sync()` runs and `wlib-refresh-library` is sent.
- **Queue**: `MoveQueue` has one worker thread, a FIFO deque, a cancel event for the current job and the totals. `status()` gives `running`, `current` (`game_id`, `title`, `bytes_done`, `bytes_total`, `speed_bps` over the last 3 s), `waiting`, `position`, `total`, and `summary` (moved, skipped, cancelled, failed, first reason) once after the queue ends; when a new batch starts before that summary is read, the next summary adds both batches and keeps the earlier first reason. A current or waiting game is busy ("This game is being moved. Wait for the move to finish."). `_game_files_busy_reason()` gives the move and uninstall reasons; launch, update install, Remove, mod tools (`_tool_run()`) and save restores (`_save_operation(writes=True)`) refuse them. An `atexit` hook stops the copy at the next file; the next start deletes the temporary folder.
- **Bridge**: `plan_game_uninstall(game_ids, root_overrides)`, `uninstall_games(game_ids, {backup_saves, remove_from_library, root_overrides})`, `plan_game_move(game_ids, dest_parent, root_overrides)`, `start_game_move(game_ids, dest_parent, root_overrides)`, `get_move_status()` and `cancel_game_move(cancel_all)`. A running game gives "Close the game before uninstalling it." (or "...before moving it.").

### Download queue (`core/downloads/queue.py`)
`DownloadQueue` keeps every in-app download, file host or torrent, in one order. It owns the slots (`download_max_active`, 1–5, default 2), the holds, the automatic retries and each job's queue state, and drives the two workers through the `Worker` interface (`prepare`, `start`, `stop`, `remove`, `snapshot`, `restore`, `unclaimed`, `set_speed_share`, `cleanup`). The workers keep their own transfer code.
- **States**: `preparing`, `queued`, `retry_wait`, `held`, `running`, `paused`, `attention`, `ready`. Only `running` uses a slot. A new job goes to the end; a game has at most one job that is not `ready`. When a slot frees, the first `queued` job in order starts. A lower slot number never stops running jobs.
- **Download now** starts the chosen job at once when a slot is free. When the running count equals the slot limit, the running job that started last and can continue gives up its slot and becomes the first waiting job. If no running job can continue or the running count exceeds the slot limit, the chosen job becomes the first waiting job.
- **Saved state**: every state and order change goes to the `download_jobs` table (see [database.md](database.md)). At startup `load()` restores the rows (a job that was `running` or `held` starts first, a paused job stays paused, and a job whose worker already finished it, such as a torrent the supervisor saved as done before the queue's next tick, becomes `ready`), deletes rows whose data is gone, adopts worker jobs that have no row at the end in creation order, removes paused or failed file-host jobs untouched for 30 days, and then lets each worker clean its staging folder.
- **Tick**: one daemon thread runs once per second while a job can change by itself (`preparing`, `queued`, `retry_wait`, `held`, `running`, or a browser check). It reads the workers, starts waiting jobs, checks retries, evaluates holds, sets the speed shares every second tick and adds one speed sample. An empty queue, or one with only paused, failed or finished jobs, has no thread.

- **Bridge** (`core/api_mixins/downloads.py`): every call returns `{"success": false, "error": ...}` on failure, and "The download was not found" for an unknown job id.
  - `get_update_download_links(game_id, site="")` reads a game's F95Zone or LewdCorner first post through the extension and returns builds with short-lived opaque mirror IDs and `archive_password` (empty when the post gives none; never logged). It reports the selected `site` and eligible `sites` with their versions. The default follows `latest_site`, with F95Zone on ties when available. LewdCorner must be active, and catalogued Premium threads need the effective LC Plus state (Yes, or Auto with Plus detected). The picker discards held URLs when closed. The parser never reads `data-proxy-href`.
  - `get_download_queue(include_history=False)` → `{jobs, queue, seeding}`. Each job has `job_id`, `kind` (`host` or `torrent`), `game_id`, `game_wishlisted` (current wishlist status, false for a missing game), `title`, `version`, `state`, `reason`, `position`, `error_code`, `error_text`, `bytes_done`, `bytes_total`, `speed`, `eta`, `retries`, `retry_at`, `retry_in`, `created_at`, `finished_at`, `can_continue`, `source` (the build identity including `site` for file hosts, or the RPDL id) and `details` (worker stage, `peers`, `upload_speed`, `seed_state`, `ratio`, `archive_path` or `folder_path`, ...). `queue` has `max_active`, `active`, `hold` (the hold in force: `game`, `battery` or `""`), `hold_reason`, `hold_override`, `hold_keeps_running` (job ids), `speed`, `peak`, `forecast` (`needed`, `free`, `unknown`, `fits`, `missing`), `settings` (the four queue settings) and, only when asked, `history` (up to 300 one-second samples). `seeding` lists the torrent snapshots that still seed.
  - `reorder_downloads(job_ids)` puts the named jobs first in that order. `start_download_now(job_id)` returns `outcome`: `started`, `yielded` or `first`. `pause_download`, `resume_download`, `retry_download` and `remove_download` take a job id; `pause_all_downloads` and `resume_all_downloads` return `count`; `resume_downloads_now()` overrides the current hold until it ends.
  - `start_update_download(game_id, link_id, replaces=None)` and `start_rpdl_download(game_id, torrent_id, version, replaces=None)` add to the queue and return `job_id`. For a wishlisted game, a non-empty job version is saved as `latest_version` after queuing so the first install uses the downloaded version. File hosts use the thread version, and RPDL uses the version supplied by the caller. `replaces` puts the new job in a failed job's place and removes that job with its data. A game that already has an unfinished download gives "This game is already in the downloads". `answer_seed_prompt` and `stop_seeding` are unchanged.
- **Failures** (`failures.py`): `classify()` maps the workers' messages to `network`, `removed`, `quota`, `challenge`, `invalid`, `disk`, `write`, `sign_in`, `extension`, `check_timeout`, `permission`, `mirror_gone`, `engine` or `unknown`. Only `network` retries by itself, after 30 s, 2 min and 10 min (`retry_at`, checked by the tick; the job uses no slot while it waits); then the job needs the user. Every other code needs the user at once.
- **File hosts** (`workers.HostWorker` over `manager.DownloadManager`): a new job resolves when it is added (one resolve at a time, outside the slots) and keeps the file-host address in memory only; the transfer runs in a slot. A start that must resolve first and needs a browser check gives up its slot; after the check it reports `prepared` and waits, as the first waiting job, for a slot before it moves data. Pause stops the transfer with `DownloadPaused`: The extension's resolve result can carry the browser's `user_agent` (1 to 512 printable ASCII characters); wLib keeps it in memory with the resolved address and sends it on every Pixeldrain, MEGA and Buzzheavier request, Range requests included (never saved, logged or shown in snapshots). A 403 with a Cloudflare `error code: 1010` body fails as a challenge (`core/downloads/network.py`), so it is not retried automatically and a resume keeps its partial file. Pixeldrain and Buzzheavier keep their `resume-<hash>.part` (named in the job's `source.part_file`), MEGA keeps nothing and starts over. After a restart, or a retry after a link failure, the job reads the thread again (`UpdateDownloads.relink`), matches the saved build (with its kind, so an old-version build cannot take its place) and mirror identity and resolves. The match must also have the job's `version` (the F95 title's version, else the starter post's, read as a thread refresh reads it): a thread that now offers another release, or (for a job saved before its identity held the mirror and the build kind) more than one matching mirror, needs the user. A file-host job relinks from its saved `source.site`. Jobs saved without a site use F95Zone. A missing extension or mirror needs the user.
- **Pacing** (`core/downloads/pacing.py`): `download_limit_kib` (KiB/s, 0 for no limit) is one limit for file hosts and torrents together. `SpeedLimiter` is a token bucket that every host transfer shares (`host_limiter`); with a limit the transfer reads a quarter-second of the rate at a time (16 KiB to 1 MiB), and each wait lasts at most 0.25 s and ends at once on cancel or pause. Every second tick, `split_limit(limit, host_running, torrent_running, host_used, torrent_used)` gives the host and torrent shares: one kind alone gets all of it, otherwise the shares follow the number of running jobs, and a side that used under 80% of its share gives the rest to the other side but keeps 10%. The two shares always add up to the limit; when both kinds run, each gets at least 1 KiB/s, except at a 1 KiB/s limit, where torrents get it and file hosts get 1 byte/s (the torrent helper cannot go below 1 KiB/s). A wait that a cancel or pause ends gives its allowance back. The torrent share goes to the helper through `set_download_limit()`.
- **Holds** (`core/power.py`): with `download_pause_while_playing` (default on) the queue holds jobs while a game runs; with `download_pause_on_battery` (default off) it holds them while `on_battery()` is true. `on_battery()` reads `/sys/class/power_supply` on Linux (on battery when no mains or USB supply is online and a system battery discharges; device batteries are ignored) and `GetSystemPowerStatus` on Windows, and returns None when it cannot tell, which counts as mains power. A hold pauses only jobs that can continue (`hold_keeps_running` lists the others) and never resumes a job the user paused. `resume_downloads_now()` ignores the current hold until it ends. The queue checks the holds again at startup and before a user action (pause, resume, retry, remove, Download now) fills a slot, so no job starts while a hold applies; after a restart under a hold, a job that was running or held stays `held`.
- **Settings** (`core/downloads/queue_settings.py`): `download_limit_kib`, `download_max_active`, `download_pause_while_playing` and `download_pause_on_battery` are device-local. `save_settings` checks all four before it saves anything (a bad value gives an error with `field`) and then calls `apply_settings()`, so a new limit or slot number applies to the running queue at once.
- **Torrents** (`workers.TorrentWorker` over `torrents.TorrentSupervisor`): a waiting torrent is a paused torrent. `start(..., paused=True, job_id=...)` fetches and checks the `.torrent` and adds it to the helper paused; the queue's `resume` moves data. A pause or resume during the `.torrent` fetch is kept and applied when the torrent is added. A torrent that finishes while it is paused, waiting or held (the helper's `finished` can come after the pause) becomes `ready` at the next tick or status read; a start that finds it finished is not a failure. `load()` no longer resumes downloads by itself. A low-disk pause and every failure map to `attention`; "engine restarting" stays `running`. Removing a torrent is one supervisor call (`TorrentSupervisor.remove`) that cancels an active or failed one, or discards a finished one, under the same lock that handles the helper's `finished` event. Removing a finished torrent deletes its folder when it is unused. If the supervisor keeps the torrent for seeding or an open install dialog, it saves the removal so startup skips queue adoption; the folder goes when the install dialog lets go of it, unless the torrent still seeds.

### Torrent downloads (`core/downloads/`)
RPDL torrents download through a separate helper process, so a libtorrent crash never takes wLib down. The main process never imports `libtorrent`.
- **RPDL client** (`hosts/rpdl.py`): sign-in (`POST /api/user/login`), public search (`GET /api/torrents`), details (`GET /api/torrent/<id>`) and `.torrent` fetch (`GET /api/torrent/download/<id>`, Bearer token). Only `https://dl.rpdl.net` is contacted, one request at a time and at least 1 s apart. A `.torrent` must be a complete bencoded dictionary of at most 14 MiB. Failures are classified (`RpdlError.kind`: `sign_in`, `not_found`, `rate_limit`, `unavailable`, `invalid_response`, `bad_login`). A 401 renews the token once with the stored password; the renewed token is saved and used only if the account is still the same (a sign-out or account change during the renewal ends with `sign_in`). Search results are cached for 24 hours in `<cache root>/wLib/rpdl-search.json`.
- **Credentials**: `rpdl_username`, `rpdl_password` and `rpdl_token` are device-local settings (`credentials.py`), absent from every backup and sync allowlist. `accounts.status()["rpdl"]` reports only `connected` and `username`.
- **Matching** (`rpdl_match.py`): pure functions. `title_score()` gives 0-100, with penalties for a different sequel number and for marker words (OST, DLC, demo, ...) the game lacks. `rank()` hides results below 40, orders by score, then version match, seeders and date, shows at most 8, and preselects one only when it scores 70 or more, has seeders, carries the update's version (`listing_has_version()`; the first copy of a number from the game title, such as the `2` in `Game 2`, is part of the name and not a version) and no other eligible result is within 8 points. When the game title has a number and the listing repeats it as the bare release version (`Game-2-2-pc` for `Game 2` at version `2`), that second copy is left out of the title score, so the listing is not mistaken for a sequel. `plan_queries()` tries the full title, then the version-free title, then title plus developer.
- **Helper** (`torrent_helper.py`, started as `wlib --torrent-helper`, dispatched in `main.py` before the API import): JSON lines on stdin (commands) and stdout (events); stderr goes to the app log. The helper writes events to the original `sys.__stdout__`, not to the app log's stdout copy, and points `sys.stdout` at stderr so stray prints cannot corrupt the protocol.
  - Commands: `hello` (options `download_kib`, `upload_kib`, `port_mapping`), `add` (`id`, `dir`, `paused`), `pause`, `resume`, `remove`, `stop_seeding`, `set_limits` (`download_kib`, `upload_kib`, optional `port_mapping`), `shutdown`.
  - Events: `ready` (with the listen `port`), `status` (all torrents, at most once a second), `finished` (sent only after libtorrent's `cache_flushed_alert` confirms the last writes; the flush is asked for again every 10 seconds, and after 5 minutes the helper drops the torrent and sends `error` with code `flush_timeout`), `error` (fixed message plus `code`), `saved`, `removed`, `stopped`, `bye`.
  - Session: DHT, local discovery and peer exchange off; UPnP and NAT-PMP only when `port_mapping` is true; the OS picks the port. Torrents whose raw paths are absolute or contain `..`, or that contain symbolic links (BEP 47 `attr` `l` or `symlink path`, in v1 file lists or v2 file trees), are refused before libtorrent sees them. Events never carry tracker paths; the `tracker` field is scheme and host only.
  - Resume data is written to `resume.dat` on pause, when a torrent finishes, every 5 minutes, on `shutdown` and when stdin closes (the helper then exits). A broken or closed stdout pipe means the parent is gone: later events are dropped and the resume saves continue.
- **Supervisor** (`torrents.py`, `TorrentSupervisor`): owns job state and the helper. The helper starts lazily; `Api()` calls `load()` and `cleanup()` at startup and registers `shutdown()` with `atexit`. Its `status()` gives each torrent's `kind: "torrent"`, `peers`, `upload_speed`, `ratio`, `ratio_target`, `seed_state`, `paused`, `hint`, `eta`, `archive_path` or `folder_path`. `find_payload()` reports an archive (the first part of a multi-part set) only when every file is part of that one archive or a small extra (readme, `.nfo`, image); anything else, such as a game folder that ships its own `.zip`, is a folder install.
  - Restart: a crashed helper restarts after 1, 5 and 15 s; a restart that cannot start the helper counts as an exit and tries again, and so does a helper that cannot start when `load()` restores jobs; more than three exits within 10 minutes marks the downloads failed ("Torrent engine keeps stopping") and keeps their data. The cutoff ends with that window, so a download started afterwards restarts a crashed helper again. Resuming a restored job starts the helper if none runs and no restart is scheduled, and fails the job with the unavailable message when it cannot start. A missing engine reports "Torrent downloads are unavailable in this build".
  - Disk: a start needs the torrent's size free; a running torrent pauses below 512 MiB free.
  - Hints: "Looking for peers" after 20 s without peers; "Connected, but no data is arriving" after 120 s.
- **Seeding** (`seeding.py`, `torrent_settings.py`): `decide_after_finish()` maps `torrent_seed_mode` (`ask`, `always`, `never`) to ask, seed or stop. `limit_reached()` compares uploaded bytes with `torrent_seed_ratio` times the size and seeding time with `torrent_seed_hours`; only time the helper reports as seeding counts. The supervisor adds only increases of the helper's upload counter to the job's uploaded bytes, and takes a new baseline each time it adds the torrent to a helper, because a restarted helper restores an older counter from `resume.dat`. `torrent_seed_*` are in `GENERAL_SETTINGS_KEYS` (backups and sync); `torrent_upload_limit_kib`, `torrent_port_mapping`, `torrent_watch_folder` and `torrent_export_warning_accepted` are device-local. Saving the upload limit or port mapping calls `supervisor.apply_limits()`; the download limit is the queue's share of the shared limit (`set_download_limit()`), and `torrent_download_limit_kib` is read only once, to seed `download_limit_kib`.
  - `seed_state` is `""`, `awaiting_answer`, `seeding` or `ended`. An unanswered question is stored as phase `awaiting_seed_answer` and asked again after a restart, with the torrent re-added paused. A torrent that finishes while paused or held seeds as the setting says: with `always` the supervisor resumes it in the helper, with `ask` it stays paused until the answer, with `never` it ends.
  - An ended torrent's folder is deleted only after an install from it succeeded (`release(path, installed=True)`) and no install holds it open. Ended torrents never installed are removed after 30 days.
- **Layout**: `downloads/torrents/<info-hash>/` holds `meta.torrent`, `resume.dat`, `state.json` (job id, game id, RPDL id, title, version, phase, error, uploaded bytes, seeding seconds, `installed`, `queue_removed`, timestamps) and `data/`. These files carry the tracker passkey, so they stay in this folder, outside backups, sync and diagnostics. On Linux and macOS, `torrents/` and each `<info-hash>/` folder are owner-only (`0700`), and `meta.torrent` and `resume.dat` are created as `0600` files. `load()` removes group and other access from folders and files that an older version made with the umask. An exported `.torrent` keeps the normal umask mode, because a client in the folder the user picked can run as a different user. `DownloadManager.cleanup()` only visits regular files in `downloads/`, so it skips this folder. Startup cleanup deletes folders with no job, and paused, failed or ended ones untouched for 30 days.
- **Install from a torrent**: `install_archive(..., source_kind="folder")` accepts only folders inside `downloads/torrents/`. A seeding torrent's files are copied; otherwise the folder is moved when staging and library share a drive (restored if the install fails before it lands). An archive inside the torrent area is never deleted by "Delete archive after install".
- **API** (`core/api_mixins/downloads.py`, mirrored in `ui/src/services/api.ts`): `connect_rpdl_account`, `disconnect_rpdl_account`, `find_rpdl_torrents(game_id, version, refresh)`, `start_rpdl_download(game_id, torrent_id, version)`, `save_rpdl_torrent`, `get_rpdl_magnet`, `send_rpdl_torrent_to_watch_folder`, `answer_seed_prompt(job_id, seed, remember)`, `stop_seeding`. Pause, resume and remove go through the queue calls above. Starting requires sign-in. A successful start for a wishlisted game saves the supplied version to `latest_version` when it is non-empty. `delete_game` calls `supervisor.forget_game()`.
- **Export** (`torrent_export.py`, `bencode.trackers()`): the user can take an RPDL torrent out of wLib for an external client. `trackers(data)` reads `announce` and every `announce-list` tier in file order, without duplicates or empty values, and skips bad entries. `magnet_link(data)` builds `magnet:?xt=urn:btih:<hex>&dn=<name>&tr=...` (percent-encoded); a v2 or hybrid torrent also gets `xt=urn:btmh:1220<sha256 hex>`, and a v2-only torrent has only that `xt`. `parse_torrent()` reads v2 `file tree` sizes; a v2-only torrent's info hash (and folder name) is its 64-hex SHA-256 hash. `safe_file_name(name, fallback)` replaces `/ \ : * ? " < > |`, NUL and control characters with `_`, removes leading and trailing dots and spaces, cuts to 150 UTF-8 bytes and adds `.torrent` (`rpdl-<id>` when nothing is left). `write_torrent(folder, file_name, data)` writes its own `.<file_name>.<random>.part` (so overlapping exports never share it), runs `fsync`, then `os.replace`; on any error it removes the `.part` file, so a watch-folder client never sees a partial `.torrent`.
  - Bridge (`downloads.py`): `save_rpdl_torrent(torrent_id, folder)` (an existing absolute folder), `get_rpdl_magnet(torrent_id)` and `send_rpdl_torrent_to_watch_folder(torrent_id)` (fails with an error that names the folder when it is unset, missing or not writable, and never starts an in-app download). All three need an RPDL sign-in (`error_code` `sign_in`), and use `ApiBase._fetch_checked_rpdl_torrent()`, the same checked fetch and info-hash comparison as `start_rpdl_download`. They log only the torrent id and the result kind.
  - Settings: `torrent_watch_folder` (blank, or an absolute existing folder; a bad value gives "Watch folder must be an existing folder") and `torrent_export_warning_accepted` are device-local (`torrent_settings.DEVICE_LOCAL_KEYS`), not in `GENERAL_SETTINGS_KEYS`, and are in the settings payload.
  - Secrets exception: these exports are the only way a `.torrent` file or magnet link leaves `downloads/torrents/`. They write only to the clipboard (in the UI) or the folder the user chose. Backups, sync, diagnostics and logs stay unchanged.
- **Packaging**: `libtorrent==2.1.1` is pinned in `pyproject.toml` and `uv.lock`; `scripts/build.sh` and `packaging/windows/wlib.spec` collect it.

### Library folders and part updates

`get_settings()` returns `library_folders: list[str]` and `library_folder: str`; `save_settings()` validates the pair together, strips empty entries and deduplicates by realpath. The default must be listed whenever the list is non-empty. Both keys may be cleared together. `list_library_folders()` returns `[{path, is_default, available, free_bytes}]`, using sandbox writability and the nearest existing parent's free space; unavailable folders have `free_bytes: null`.

`inspect_archive` returns the chosen `library_folder` and `own_targets_inside` (other target labels inside the replaced folder). Without an explicit folder, updates choose the deepest listed folder containing the replaced part, falling back to the default. `preview_install_destination` accepts `library_folder` in its options. `install_archive(options)` accepts `library_folder` and `target_id`; an explicit folder must still be listed by realpath. Staging, disk-space checks and the final rename use that folder. Folder choices do not change the saved default.

A null/omitted `target_id` updates the default executable. A numeric ID must belong to `game_id`; saves and old-folder handling follow that target. Only the chosen target is directly repointed; other targets and the default move when their relative executables exist in the new install. Game version/engine and an in-folder save override still update on the game row. Cleanup protects every listed library folder and keeps the old install when any own target remains inside it after relocation, naming the target in `kept_old_folder_reason`.

Path-setting backups export `library_folders` as a native JSON list beside `library_folder`. Import filters foreign paths per entry with `foreign_path` warnings, chooses a surviving default, supports older default-only backups, and preserves a local pair in fill-missing mode.

### `core/game_saves.py` (Game Saves Folder)
Pure functions over explicit paths (testable against `tmp_path`); `core/api_mixins/saves.py` resolves the folder from the stored game row and calls in, so the frontend never sends a path that Backup or Import writes to.
- **Detection**: `detect_save_locations` holds the former `find_save_files` body, which stays as a wrapper on `Api`. Entries carry `eligible`; the game's own executable folder is `eligible: false` (a lead only). `resolve_effective_folder` picks the override, else the single eligible detected folder, else none.
- **API**: `get_game_saves(game_id)` (override, detected, effective folder, backups, retention), `set_game_save_folder(game_id, path)` (empty clears; `~` expanded; absolute only; not inside `save-backups/`; not an existing file; may not exist yet), `backup_game_saves(game_id)`, `import_game_saves(game_id, source)`, `restore_game_saves_backup(game_id, backup_name)`, `open_game_save_backup(game_id, backup_name)`. Opening the saves folder itself uses `open_folder`. Prefix and runner feed detection only for non-`native` launch modes. `backup_name` must match the timestamp pattern and resolve inside the game's backup folder.
- **Layout**: `<data dir>/save-backups/<game id>/<YYYY-MM-DD_HH-MM-SS>[-N]/` holds plain folders in local time. Copies go to a `.<name>.partial` sibling and are renamed into place; any failure removes the partial folder. Symlinks are skipped and counted. Listing and pruning only see pattern-named folders, so a user's own folders there are untouched. A save-editor backup taken from the game's own RPG Maker `save` folder while the effective folder is elsewhere gets a hidden `.<name>.source.json` note (with the backup folder's device, inode and ctime); restoring that backup, and the safety backup that restore makes, goes back to `<data root>/save` instead of the effective folder. The safety backup's note is written before the first restore write (before the retention prune); when the note cannot be written, that backup is removed and the restore stops without changes. A note that does not match its folder is ignored, and a restore is refused when that `save` folder can no longer be found. Removing a game moves its backups to `save-backups/removed/<game id>_<timestamp>/`, so they stay on disk but a later game with the same ID does not inherit them. Removing a game that is running, being installed, restored or changed by a mod tool is refused (`game_running` / `game_busy`).
- **Retention**: the `save_backup_keep` general setting is `all` (default) or `1`–`99`. After each successful backup, including pre-import ones, the game's oldest backups beyond the limit are deleted, never the one just made. Restoring also protects the backup being restored.
- **Import**: merge copy (same-named files overwritten, others kept). The source may not be, sit inside, or contain the saves folder; a file/folder type conflict stops it before any write. A non-empty target is backed up first and the import stops if that fails. The merge itself is not atomic, so the error names the backup.
- **Concurrency**: backup, import and restore hold a per-game guard (`Api._saves_busy`); a second call returns "A save operation is already running for this game". Calls block only their own PyWebView thread.
- **Backups and sync**: `save_path_override` exports with the launch-configuration section (path warning when missing, still imported) and never reaches the sync file. Save backups are never exported.

### Game mod tools (`core/game_tools.py`, `core/renpy_tools.py`, `core/rpgm_tools.py`, `core/rpgm_plugins.py`, `core/rgss_tools.py`, `core/unity_tools.py`)
Pure functions over explicit folders (testable against `tmp_path`); `core/api_mixins/game_tools.py` resolves the folder from the stored game row, so the frontend never sends a game path. Only the output folder for separate-folder extraction comes from the user. `core/game_tools.py` also holds the shared extraction safety helpers (`is_inside`, `validate_output_folder`, `safe_relative_parts`, `resolve_destination`, `export_root`, `nearest_existing`, `check_free_space`) used by both Ren'Py and RGSS extraction.
- **Detection**: `game_tool_folder(row)` is the executable's folder (`Api._get_urm_game_dir` uses it). `detect_engine` reads the files on disk and ignores the stored engine label: `renpy/` plus `game/` is Ren'Py (`"renpy"`); the first of `<folder>/www` or `<folder>` holding `data/System.json` is the RPG Maker MV/MZ data root (`"rpgm"`); a top-level `.rgssad`/`.rgss2a`/`.rgss3a` archive (with or without `.wlib-backup`) or `Data/Scripts.{rxdata,rvdata,rvdata2}` (letter case ignored) is RPG Maker XP/VX/VX Ace (`"rgss"`, checked after MV/MZ and before Unity); Unity (`"unity"`) is a `UnityPlayer.dll`/`UnityPlayer.so` or a `<exe>_Data` folder with `globalgamemanagers`, `data.unity3d` or `mainData`; `detect_engine` only checks that layout (`is_unity_folder`), while `detect_unity` also reads the platform, scripting backend, architecture (PE machine field) and Unity version for `get_game_tools`.
- **API**: `get_game_tool_support(game_id)` (`engine`: `"renpy"`, `"rpgm"`, `"rgss"`, `"unity"` or `""`; cheap, decides whether the Tools tab exists), `get_game_tools(game_id)` (full tab state: Ren'Py console state, archive list with size and format, URM status; RPG Maker MV/MZ encrypted counts, missing copies, key source, switch state, backup present; RGSS archive list with size, format, support flag and entry count, missing/differs counts, switch state and backup flag), `set_renpy_console(game_id, enabled, developer)`, `extract_renpy_archives(game_id, options)` (`{"mode": "folder" | "in_place", "output": str}`), `decrypt_rpgm_assets(game_id)`, `set_rpgm_use_decrypted(game_id, enabled)`, `extract_rgss_archives(game_id, options)` (`{"mode": "folder" | "in_place", "output": str}`), `set_rgss_use_extracted(game_id, enabled)`, `get_game_tool_status(game_id)` and `cancel_game_tool(game_id)`. The plugin list has its own methods: `get_rpgm_plugins(game_id)` (read only, apart from `get_game_tools`) returns `{success, engine, readable, reason, revision, entries, backup}`, where `engine` is `"mv"`, `"mz"` or `"unknown"`, `backup` is `{state, reason}` and an entry is `{index, name, description, enabled, loaded, can_enable, needed_by, issues}` with issues `{code, level, names[, direction]}`; `set_rpgm_plugin_enabled(game_id, index, enabled, revision)` and `restore_rpgm_plugins(game_id, revision, replace_changed)` run through `_run_game_tool(game_id, "rpgm", "plugins", ...)`, check the argument types (`bool` is not an index), and return the new state on success. A stale revision returns `{success: false, code: "stale", error}`; a list that cannot load returns `success: false`. Unknown ids return `success: false`; an action on a game of the wrong engine is rejected.
- **Unity**: Unity tools expose `list_bepinex_versions(game_id)`, `install_bepinex(game_id, options)`, `uninstall_bepinex(game_id, options)` and `restore_bepinex(game_id)`. Downloads use `bepinex-cache/` in the data dir (SHA-256 checked when GitHub publishes a digest); IL2CPP installs also place the Unity base libraries in `BepInEx/unity-libs/` so the first launch needs no internet. Uninstall removes folders it leaves empty. Installations preserve plugins, configuration, patchers and Unity libraries, and back up replaced files. An install after an uninstall that kept user data keeps the uninstall's backup and records the new build's files in it, so Restore sets the new build aside and brings back the earlier one. Linux-native Unity installations are detected but not supported for BepInEx actions.
- **Runs**: every action goes through `Api._tool_run`: one run per game (`A tool is already running for this game`) and none while `get_running_games()` lists the game. This covers plugin switches and plugin list restores too, and `_game_busy_reason` refuses a launch while one runs. Status (`running`, `action`, `done`, `total`, `current`, `cancel`) lives in `_tool_status` under a lock and is dropped when the run ends, even after an exception. Extraction and decryption block their own PyWebView thread while the Tools tab polls `get_game_tool_status` every 500 ms; `cancel_game_tool` sets the flag the engine callback reads, checked between files and between chunks. Files written before a cancel are kept, and no `.wlib-partial` file is left behind.
- **Console** (`renpy_tools`): `game/zzz_wlib_console.rpy` sets `config.console = True` (and `config.developer = True` with developer mode) in an `init 999 python:` block. State is `off` (neither file), `on` (the `.rpy` without the developer line, or only the `.rpyc`) or `developer`. Changing the mode rewrites the script and deletes the stale `.rpyc`; turning it off deletes both.
- **RPA safety rules**: archive contents are untrusted. The index is read with a `pickle.Unpickler` subclass that allows only the two callables pickle protocol 2 uses for bytes, each restricted (`_codecs.encode` with latin-1 only; `bytes()` with no arguments only, for the empty prefix rpatool writes), and raises for everything else (`pickle.loads` is never used); the archive is then reported as unsupported and nothing runs. The index is inflated with a 64 MiB cap. RPA-2.0, 3.0 and 3.2 headers are read (3.0: XOR of the hex fields after the offset; 3.2: after one ignored field; anything else, including RPA-1.0, is unsupported). Entry data is the prefix followed by `length` bytes from `offset`; as in Ren'Py's own loader, `length` does not count the prefix. Entries whose data lies past the end of the archive are skipped. Entry paths are turned into `/`, then absolute, drive, empty or `..` paths are skipped, and the `realpath` of the destination's parent must stay inside the target root (this also stops a symlink planted in the target). Files are copied in 1 MiB chunks to `<dest>.wlib-partial` and renamed into place. `0x52_URM.rpa` is never listed or extracted.
- **Extraction modes**: `folder` writes `<output>/<archive name without .rpa>/` (overwriting same-named files there); `output` must be an existing absolute folder outside the game folder. `in_place` writes next to each archive, skips `.rpy`, `.rpyc`, `.rpym` and `.rpymc` (a loose copy of an archived script could define its labels twice) and never replaces an existing file. Free space on the target drive is checked before the first write. The result carries `files`, `bytes`, `skipped` (with `skipped_scripts`, `skipped_existing`, `skipped_unsafe`, `skipped_invalid`), `failed`, `unsupported` and `cancelled`; a `PermissionError` stops the run with its message.
- **RPG Maker decryption** (`rpgm_tools`): `.rpgmvp`/`.png_` become `.png`, `.rpgmvo`/`.ogg_` become `.ogg`, `.rpgmvm`/`.m4a_` become `.m4a`, next to the originals (kept). A file is decrypted only when it starts with `RPGMV` and is at least 32 bytes; both tools accept existing copies that point to readable regular files, preserve those copies, and report blocked paths. The key is `encryptionKey` from `System.json` (read with `utf-8-sig`, 32 hex digits); when it is missing or malformed it is recovered from the first encrypted image's PNG header and confirmed on a second image when one exists (audio alone cannot recover a key). Decryption streams: the 16-byte header is dropped, the next 16 bytes are XORed, the rest is copied through `.wlib-partial`.
- **"Use decrypted files in-game"**: turning it on is refused while any really-encrypted asset lacks its copy (the error gives the count). It copies `System.json` to `System.json.wlib-backup` once (never overwritten), sets `hasEncryptedImages` and `hasEncryptedAudio` to `false`, and writes the file back minified with key order kept. Turning it off restores both flags to their values in the backup (`true` when there is no readable backup), so a game that encrypted only its images keeps `hasEncryptedAudio` false, and keeps the backup. The switch reads as on exactly when both flags are `false`.
- **RGSS archive extraction** (`rgss_tools`): discovers top-level `.rgssad`, `.rgss2a` and `.rgss3a` archives (letter case ignored, with or without `.wlib-backup`; subfolders are not searched) and chooses the format from the 8-byte header (`RGSSAD\0` + version `1` for `"RGSSAD v1"` or `3` for `"RGSSAD v3"`), not the file extension. Any other header, version byte, or invalid/truncated index (name length 0 or > 4096, > 200,000 entries, truncated v3 index or truncated v1 header) marks the archive unsupported. Entry names decode as UTF-8, falling back to `cp932` (Shift-JIS), with `\` normalized to `/`; undecodable names or data past EOF are skipped and counted (and end the walk in v1). Decryption streams in 1 MiB chunks through `.wlib-partial` using an `array("I")` keystream and big-int XOR, with cancel checks between chunks and free-space and path-escape checks shared with Ren'Py.
  - **Extraction modes**: `folder` writes `<output>/<archive stem>/` (overwriting same-named files there; `output` must be an existing absolute folder outside the game folder) without touching the game folder. `in_place` writes every entry, data and scripts included, under the executable's folder without overwriting existing loose files (first archive in name order wins; archives stay in place).
  - **"Use extracted files in-game"**: turning it on renames every plain archive `<name>` to `<name>.wlib-backup`, and turning it off renames every `.wlib-backup` back to `<name>`, rolling back earlier renames if a later rename fails. It refuses to turn on while any safe entry has no regular loose file (giving the count) or any listed archive is unsupported, and refuses either direction when a rename target already exists. The switch reads as on exactly when at least one `.wlib-backup` archive exists and no plain archive exists. `missing` and `differs` (size-only) are counted across safe entries of supported archives.
- **RPG Maker MV/MZ plugin list** (`rpgm_plugins`): reads, checks, switches and restores `<data root>/js/plugins.js`. Nothing is stored: each load reads the files again. Game updates do not keep plugin changes; an update install puts a new list in place.
  - **Grammar**: the bytes must be UTF-8 (a BOM stays in the text) and at most 4 MiB. The text must be `[BOM] (space | comment)* [var|let|const] $plugins = <JSON array> (space | comment)* [;] (space | comment)*` and then the end of the file. A linear scanner skips `//` and `/* */` comments (no regex runs over the whole file). `json.JSONDecoder.raw_decode` reads keys and values, and a walk over each entry's top-level keys records the character span of `status`, so `"status":true` inside a parameter is never taken. Each entry must be an object with exactly one text `name` and exactly one boolean top-level `status`. Other lists are unreadable, with a reason: code before or after the array, a trailing comma, single quotes, an invalid escape, an unclosed comment, `NaN`/`Infinity`, nesting too deep (`RecursionError`), a duplicate or non-boolean `status`, non-UTF-8 bytes, too large, missing. An unreadable list is a successful load with `readable: false`, so Restore stays available.
  - **Engine rules**: `mz` when `js/rmmz_managers.js` exists, `mv` when `js/rpg_managers.js` exists, else `unknown`. The load key is the name after the last `/` only when the MZ script contains `extractFileName(plugin.name)` (newer MZ); older MZ, MV and unknown engines compare full names. The first entry that is on for a key loads; later ones that are on do not (`duplicate`). The file is `js/plugins/<full name>.js`, looked up per path part against directory listings (one listing per folder per load), so the result is the same on case-insensitive hosts.
  - **Checks**: `missing_file` (warning when the entry loads, note when it is off), `unsafe_name` (warning: absolute, drive, backslash, NUL, empty or `..` parts, or a path that resolves outside the data root; the file is not read), `case_mismatch` (note: the file exists only with other letter case), `duplicate` (note; a duplicate gets no other issue). MZ only, for loaded entries: all `/*:` header blocks in every language are read (`/*~struct~` blocks are not), up to 8 MiB per file; `@base`, `@orderAfter` and `@orderBefore` values run to the end of the line without white space or a closing `*/`, duplicates join, a self-reference is ignored, and values are mapped with the load key. `missing_dependency` names `@base` keys that do not load. `wrong_order` (with `direction` `after` or `before`) names loaded plugins that an order tag puts on the wrong side; `@base` alone sets no order, and a target that does not load gives no warning. `needed_by` lists the loaded direct `@base` users, and is empty when a later entry that is on has the same key (it takes over). `missing_file` and `unsafe_name` block only switching on.
  - **Revision and writes**: `revision` is the SHA-256 of the list bytes (empty when the file is missing). `set_plugin_enabled(root, index, enabled, revision)` and `restore_plugins(root, revision, replace_changed)` read the file again and compare the revision, and compare it again directly before each `os.replace`; a mismatch raises `StalePluginList`. A switch replaces only that entry's status span with `true` or `false`, parses the new bytes again and requires that only that status differs. A switch to the current value changes nothing. Writes go through `create_temp_file()` in the same folder, binary mode, flush, `fsync`, a copy of the permission bits and `os.replace`; `finally` removes the temporary file, so a failed write or replace keeps the original.
  - **Safe paths**: `<root>/js` must resolve inside the data root. The list and the backup must be regular files and not symlinks; they are opened with `O_NOFOLLOW` and `O_NONBLOCK` and checked with `fstat`, so a FIFO cannot block. Names and descriptions sent to the UI have unpaired surrogates replaced; parameters are never sent.
  - **Backup**: `js/plugins.js.wlib-backup` is made from the original bytes before the first write and never overwritten. When it cannot be written, the list is not changed. A symlink or other non-regular object at the backup path refuses switches. `backup.state` comes from a compare: `none` (no backup), `invalid` (not a regular file or not a readable list; Restore is off with the reason), `same` (same bytes), `toggles` (equal after every status token is masked), `changed` (any other difference, or the current list is unreadable or missing).
  - **Restore**: allowed for `toggles` at once and for `changed` only with `replace_changed=True` (the backend enforces it). It makes the list byte for byte equal to the backup and keeps the backup. It is refused for `none`, `invalid` and `same`, and when the list path is a symlink or not a regular file.

### RPG Maker save editor (`core/rpgm_saves.py`, `core/rgss_saves.py`, `core/ruby_marshal.py`, `core/_save_io.py`, `core/lzstring.py`)
Reads, edits and rewrites RPG Maker MV (`fileN.rpgsave`), MZ (`fileN.rmmzsave`), XP (`SaveN.rxdata`), VX (`SaveN.rvdata`) and VX Ace (`SaveNN.rvdata2`) slot saves.
- **MV/MZ codecs (`core/rpgm_saves.py`, `core/lzstring.py`):** MV is LZString Base64 text (`core/lzstring.py`, an in-house port tested against reference JS output); MZ is zlib-deflated JSON stored as a UTF-8 "binary string". Read files in binary mode. Data that does not decode to a JSON object raises `UnsupportedSaveFormat`.
- **RGSS codec (`core/ruby_marshal.py`):** pure-Python Ruby Marshal 4.8 reader (`load_all`, `load_prefix`) and writer (`dump_all`) for untrusted data; never executes code or loads classes. Enforces a 32 MiB size cap, depth limit of 256, 4,000,000 node limit, and length bounds, raising `MarshalUnsupported` for bad versions, unknown tags, `d` (data) tags, truncation, or trailing bytes. Object links (`@n`) resolve by Python identity and are renumbered dynamically on write (including `I`-wrapped `u` objects); scalars retain original wire bytes while unedited so unedited saves write back byte-identically. `assign_ids()` and `project_dumps()` produce deterministic preorder node ids and a JSON-serializable raw tree with `editable: true` only on edit-safe scalars (excluding links, symbols, hash keys, `u` blobs, non-UTF-8 strings, strings with a named `encoding` marker such as Shift_JIS, US-ASCII (`E: false`) strings with non-ASCII bytes, non-finite floats, and integers outside JS safe range). `StringNode.set_text()` encodes new text in the string's own encoding (`E: true` and unmarked strings as UTF-8, `E: false` as ASCII).
- **RGSS layouts and curated view (`core/rgss_saves.py`):** engine layout is chosen from the extension: XP is 12 dumps (frame count dump 1 at 40 fps, switches 3, variables 4, actors 7, party 8, `@sp`, 6 bonus ivars, `@exp` + `@exp_list`), VX is 14 dumps (frame count dump 1 at 60 fps, switches 6, variables 7, actors 9, party 10, `@mp`, 6 bonus ivars, `@exp` + `@exp_list`), and VX Ace is 2 dumps (header with `:playtime_s`, contents hash with `:switches`, `:variables`, `:actors`, `:party`, `@mp`, `@param_plus[0..7]`, `@exp` hash). Class names (`Game_Party`, `Game_Actors`, `Game_Actor`, `Game_Switches`, `Game_Variables`) are verified per section, falling back to `missing` while keeping the Raw view usable. Each curated leaf carries its node `ref` (or `null`) so curated and Raw edits collapse onto the same `ref:<id>` key.
- **Names:** MV/MZ `load_names()` reads `Items/Weapons/Armors/Actors/Classes/System.json` from `<data root>/data/`. RGSS `load_rgss_names()` reads `Data/{Items,Weapons,Armors,Actors,System}.<ext>` from loose files first (case-insensitive) and otherwise from the game's RGSS archive via `rgss_tools.read_entry(folder, name, max_bytes)` (plain or `.wlib-backup`). Escape codes are stripped, blank names skipped, VX Ace `@itype_id == 2` items are marked as key items, and missing/unreadable files fall back to empty lists and per-engine defaults (including `mp_label: "SP"` for XP).
- **Patches:** edits arrive as `set` (MV/MZ), `set_node` (RGSS editable scalars, preserving type and string encoding markers; text that the marker cannot hold, such as non-ASCII text in a US-ASCII string, is refused with `invalid_patch` before the backup), `set_count` (0 removes the key), `set_switch`, `set_variable` (pads with `nil` in RGSS) and `set_actor`. In MV/MZ, a level edit rewrites `_exp[classId]` from `exp_for_level()`, respects class/actor level caps, and adds passed `learnings` skills to `_skills`. In XP and VX, a level edit sets `@exp` from `@exp_list[level]` when present; VX Ace leaves experience unchanged.
- **Slots:** MV/MZ `list_slots()` lists `<data root>/save` plus the effective saves folder. RGSS `list_slots()` lists `Save<N>.{rxdata,rvdata,rvdata2}` (case-insensitive) from the executable folder, `Save`, `Saves`, `savedata`, then the effective folder (first folder wins on duplicate names; deduplicated by real path). `resolve_slot()` addresses files by name only.
- **Safe write (`write_save` via `core/_save_io.py`):** both editors share `reject_symlink()`, `read_fingerprint()` (size, mtime_ns, device, inode, SHA-256), and `atomic_replace_checked()`. Order: reject symlinks, read and fingerprint, size/mtime check, revision check (the `revision` from `load_save()` must equal the SHA-256 of the bytes read now, so a slot replaced after it was opened with the same size and mtime is refused with `changed`), decode and patch, back up, encode, verify by decoding (`==` for JSON, `trees_equal()` for Marshal), write temp file + `fsync`, recheck fingerprint, then `os.replace`. Any failure leaves the original untouched and removes temp files.
- **Backup and restore (`core/api_mixins/saves.py`):** for an RGSS slot in the executable folder, `backup_saves()` copies only `loose_save_files(folder)` (never game files such as `Game.rgss3a` or `Graphics/`); slots in `Save`, `Saves`, or `savedata` back up that subfolder; effective-folder slots back up the effective folder. Backups from the executable folder or those three subfolders write a `.source.json` note with `source = "rgss_game_save:<relative>"` (`""`, `"Save"`, `"Saves"`, or `"savedata"`). `restore_game_saves_backup()` restores into `<exe folder>/<relative>` (also passing `backup_files` for loose-only safety backups in the executable folder), refuses with a manual-copy message if the folder is gone or the game is no longer RGSS, and ignores unknown relative values by treating them as effective-folder backups.

API methods in `core/api_mixins/saves.py` (mirrored in `ui/src/services/api.ts`): `list_rpgm_saves(game_id)`, `load_rpgm_save(game_id, file)` and `write_rpgm_save(game_id, file, patches, size, mtime_ns, revision)`. The load returns `size`, `mtime_ns` and `revision` (the SHA-256 hex digest of the bytes it decoded); the write needs all three, and a missing or malformed `revision` returns `invalid_patch`. `_rpgm_save_context()` dispatches both `"rpgm"` and `"rgss"` engines. `mtime_ns` is a string because nanosecond timestamps exceed JavaScript's safe integer range. Writes run inside `_save_operation(game_id, writes=True)`. Failures return `error_code`: `game_not_found`, `unsupported_engine`, `not_found`, `unsupported_format`, `invalid_patch`, `changed`, `backup_failed`, `game_running`, `busy`, `read_failed`, `write_failed`.

### `core/game_attachments.py` (Attachments)
Pure filesystem storage behind the attachment bridge; `core/database.py` stays free of file I/O.
- **Location**: `<data dir>/attachments/<game id>/` holds copied PDF, TXT and MD files; the filesystem is the only source of truth, so files deleted by hand disappear from the list. Listing returns regular non-dot PDF, TXT and MD files as `{name, size}` sorted case-insensitively by name.
- **Adding**: `add_attachment` accepts `.pdf`, `.txt`, and `.md` case-insensitively; PDFs require a `%PDF-` signature and text files must have no NUL in their first 8 KiB. It picks a free `name (N).ext` on collisions (cutting the stem so the name stays within 255 bytes), copies through a short random `.<hex>.part` temp file with `os.replace`, and removes the temp file on failure. The original file is left untouched. Attaching takes effect immediately without Save Changes.
- **Names**: `resolve_attachment` and `remove_attachment` reject empty names, path separators (`/`, and `\` on Windows only, matching what `os.path.basename` keeps when adding), NUL, `.`/`..`, and leading dots. Opening requires the realpath parent to equal the game folder; removing deletes the folder entry itself, so removing a symlink never deletes its target. Both raise a distinct missing-file error (`attachment_missing`) when the file is gone. Open and remove act only inside the game's folder.
- **Cleanup**: `Api.delete_game` calls `remove_game_attachments` after a successful DB delete (logged, never fails the delete). `apply_library_backup` calls `prune_orphan_attachments` with the remaining game IDs after the commit when `deleted > 0`, covering sync and mirrored imports. `Api.__init__` prunes once after `init_db()` inside try/except with logging. `prune_orphan_attachments` and `remove_game_attachments` delete only all-digit subfolders for IDs not in the library; anything else under `attachments/` is left alone. Before that prune, a mirrored apply moves each deleted game's folder to device-local `attachments/held/<sync uid>/` and gives it back when a game with that sync UID is re-created (for example by a snapshot restore); held folders are removed at a later mirrored apply once no sync snapshot names that UID, and are never exported or synced. If that move fails, the folder stays in place, is left out of that prune, and gets a hidden `.wlib-held-uid` file with the sync UID. The same record also goes to memory and to the device-local `attachments_pending_holds` setting first, so a marker that cannot be written (for example on a full drive) still protects the folder. Later prunes (including the startup prune) retry the move instead of deleting the folder, and re-creating a game with that UID takes the files back; a mirrored apply scans for these folders once (`pending_holds_by_uid`), not once per re-created game. A merge into an existing held folder moves the marker last, so a failed file move leaves the marker in place.
- **Backups**: JSON exports and cloud sync carry notes and links but never attachment data or attachment names; importing or syncing keeps attachments of games that remain.

### `core/library_backup.py` (JSON Migration)
This module serializes and imports semantic library backups without copying the raw SQLite database.
- **Format**: Writes one JSON document with `format`, `format_version`, export timestamp, selected sections, game metadata, optional game sections, and selected settings groups.
- **Always-included metadata**: Every exported game includes title, developer, engine, tags, F95 URL, version fields, thread completion flag, store links, screenshot URLs, and cover reference so records remain identifiable after migration.
- **Import matching**: Matches games by normalized F95 thread identity first, then by a shared exact store identity, then by normalized title/developer only when there is exactly one local match. Records carrying only a title match a unique same-title local game without an F95 URL or developer, and a record whose thread URL is unknown locally merges into a unique URL-less local game with the same title/developer. Ambiguous fallback matches are skipped and reported. Backups without a `selected_sections` manifest offer every game section the records actually carry.
- **Merge behavior**: Matched games receive backup values for always-included metadata and selected optional sections. Unselected sections preserve local values. Playtime is overwritten from the backup when user state is imported, never summed.
- **Safety boundaries**: The JSON export excludes cookies, webview storage, downloaded runtimes, extension copies, caches, local cover files, cover cache files, save backups, game attachments (PDF, TXT, MD), and diagnostics.
- **Cross-platform paths**: Inspection reports missing executable paths and foreign global path settings. Import skips global settings whose path syntax belongs to the other OS; per-game paths and launch options remain available to edit after migration.

### `core/launcher.py` (Process Management)
This module handles native host launching and Linux compatibility runtimes.
- **Environment Overrides (Linux)**: Per-game Japanese locale and Wayland settings modify the `env` dictionary passed to `subprocess`. Windows ignores the Wayland flag and removes Wine/Proton environment variables from native launch environments.
- **Japanese locale on Windows (Locale Emulator)**: With `run_japanese_locale` on, a Windows `.exe` target starts as `[LEProc.exe, game.exe, *args]` (`locale_emulator.wrap_command`) with the game folder as the working directory. `LEProc.exe` joins the arguments after the game path with plain spaces, so each argument that is empty or has a space, tab or `"` is quoted once more with `subprocess.list2cmdline`; the game gets the original argument boundaries. With `%command%`, the arguments before it stay the user's wrappers and the arguments after it go through `LEProc.exe`. The Sandboxie wrap puts `Start.exe /box:<box>` in front of this command. `locale_emulator.get_status()` is checked first: when it is not `ready`, the launch returns `{success: false, code: "locale_emulator_missing", error}` (the error points to Settings > Running games > Japanese locale) before any process, running entry, job or playtime exists. `.bat`, `.cmd`, `.jar`, HTML and built-in web player targets do not use Locale Emulator and do not check for it; the line `Locale Emulator skipped: <kind> targets are not supported` goes to the app log and the debug launch log. `LEProc.exe` starts inside the game's Job Object and the game it starts stays in that job, so playtime, the running state and Stop follow the game (VM check: `LEProc.exe` waits for the game; an elevated game relaunches `LEProc.exe` through UAC and still ends up in the job). Alternate launch targets get the same behavior through `core/game_launch.py`.
- **Launch Modes**: Windows exposes `auto`: `.exe` runs directly, `.bat`/`.cmd` uses `cmd.exe /d /s /c "call <script> <args>"` (the script path is always quoted, and each argument that is empty or has a space, tab, `"`, `&`, `|`, `<`, `>` or `^` is quoted with inner `"` doubled, so `cmd.exe` does not split a path such as `C:\Games\A&B\Start.cmd`; wrappers before `%command%` stay outside), `.jar` uses `java -jar` with Java on `PATH`, and `.html`/`.htm` opens in the default browser. Linux additionally supports `native`, `wine_proton`, `rpgmaker_linux`, and `custom`. In Linux `auto` (Auto Detect), wLib checks host-native targets first (`execute_host_native`: built-in web player, `.sh`, `.jar`, `.html`/`.htm`, executable native ELF or script binaries), then calls `core/rpgmaker_runner.resolve_auto_runtime()` before falling back to Wine/Proton. The resolver checks in order: (1) non-Linux or non-`.exe` extension -> `default`; (2) `auto_inject_ce`, `custom_prefix`, or per-game `proton_version` set -> `default` (stay on Wine/Proton); (3) `runner_engine(game_dir)` (with the `www` -> parent adjustment when `../package.json` exists) matches no engine under the upstream runner's rules (`www/` + `package.json` + `www/js/plugins.js` -> `mv`, `data/` + `package.json` + `js/plugins.js` -> `mz`, `Game.ini` + `Game.exe` -> `mkxpz`) -> `default` (RPG Maker 2000/2003 and non-RPGM games stay on Wine/Proton); (4) RPGMaker Linux runner not detected -> `default`; (5) `mkxpz` engine with `mkxpz_status()` not installed -> `default`; (6) `mkxpz` engine with `sandboxed` and `runner_overlay_supported(bwrap, mkxpz_dir)` false -> `default`; (7) otherwise -> `rpgmaker_linux`, which runs `execute_rpgmaker_linux_runner()` with the same argument, Japanese locale, sandbox, and MangoHud skip behavior as explicit `rpgmaker_linux` mode. Custom Command uses `command_line_args` as the full command, substitutes `%command%` tokens with the absolute target, and runs in the game folder with a clean host environment. Leading `NAME=value` assignments are applied without a shell. Empty commands are rejected. Windows command-line arguments use Windows quoting rules. A Windows game that needs administrator rights (error 740) is started again through UAC (`ShellExecuteEx`), which cannot pass an environment: when the launch options set `NAME=value` overrides, the launch fails with an error that names them instead of starting the game without them.
- **Built-in Web Player**: `resolve_web_player()` in `core/web_launch.py` (re-exported by `core/game_launch.py`) decides whether an `.html`/`.htm`/`.swf` target opens in the built-in player or the system browser (`.swf` is always built-in; HTML follows the per-game `html_player` value, then the `html_builtin_player` setting, which reads as on when absent; Wine/Proton, Custom Command and the RPGMaker runner on Linux are not web launches). The built-in player is the wLib binary in a `--play-web --root <game dir> --entry <relative path> --profile <storage dir> --title <title> [--flash] [--offline] [--links open|ignore] [--devtools] [--sandboxed]` mode (`core/web_player.py`, dispatched from `main.py` before `core.api` loads) and runs through `execute_process`, so the sandbox, No internet, GameMode/MangoHud, playtime, running state and Stop apply. It serves the game at `wlib-game://game/` (one stable origin per game, with a per-game QtWebEngine profile in `<data dir>/web-player/<id>/`, outside the sandbox home) and bundled Ruffle at `wlib-game://ruffle/` (`ui/dist/ruffle/`). When a requested path does not exist exactly, `resolve_under_root()` looks it up again with each folder and file name matched by `lower()` (exact names first, then variants in sorted order, going back to try the next folder variant when one has no match; at most 64 path parts and 256 tries; folder lists are cached per folder mtime; parts with a Windows drive such as `C:` are refused), so games made on Windows work on case-sensitive file systems; the root and symlink-escape checks still apply. Sandboxed launches bind the profile folder read-write and wLib's own files read-only, and set `QTWEBENGINE_DISABLE_SANDBOX=1`; `--offline` also blocks `http(s)`/`ws(s)` requests inside the player, and sandboxed or offline players drop external links (when external links are enabled, HTTP and HTTPS links open in the system browser and `mailto:` links go to the default mail handler). In Flatpak the player runs inside the app (not through `flatpak-spawn --host`); sandboxed launches use `flatpak-spawn --sandbox` with only the game and profile folders exposed. The first built-in launch of an HTML game that follows the default returns `notice: "html_player_first_use"` once (device-local `html_player_notice_shown`). The launcher adds `--devtools` when `web_player_devtools_enabled()` is true (`web_player_devtools` setting, absent reads as on); the flag reaches sandboxed and Flatpak launches inside the player argv. With it, F12 toggles a DevTools pane: the player window is a horizontal `QSplitter` holding the game view and, after the first F12, a DevTools view (`page.setDevToolsPage`) that uses the game's own profile, loads only `devtools://` pages and sends other links through the same link rules as the game. Fullscreen applies to the splitter, so the pane stays as it is. The Ruffle bootstrap is a script on the game page only, so it never runs in DevTools. Without the flag, F12 goes to the game and the context menu has no "Inspect". Removed games' player storage moves to `web-player/removed/` and is pruned after 30 days with the sandboxes. System-browser launches stay untracked (no sandbox, No internet or Stop).
- On the first download or file pick, the built-in web player creates `exports/` inside the game’s profile. Launches with `--sandboxed` save Blob and `data:` downloads there automatically, number duplicate names, and show the saved path with **Copy path**. Other launches show a Save as dialog starting in `exports/` and offer **Open folder** after the download finishes. The game’s file picker starts in `exports/` and remembers the last selected folder for the session when the game runs outside the sandbox. The exports folder is included in web-player save backups and moves with the profile when the game is removed. Library exports and sync exclude it.
- **Built-in player video check (`core/web_video.py`)**: The PyPI Qt WebEngine build has no H.264, H.265 or AAC decoders. `Api.launch_game` adds `check_web_media: True` to its `launch_tracked` request, which passes it to `Launcher.launch` only when the resolved target is an HTML file that opens in the built-in player. The Steam launch runner never sets it, so its launches start the player as before. In the built-in player branch, for an `.html`/`.htm` target with a game id, `launch_check()` walks the served folder (`.mp4`/`.m4v`/`.m4a`, case-insensitive; symlinks that leave the folder are skipped) and reads each file's MP4 headers in Python: top-level boxes with 32-bit or 64-bit sizes, `moov` at the start or the end (at most 64 MiB of it), then the `stsd` sample entries of each track. `avc1`/`avc3`/`hvc1`/`hev1` and `mp4a` need conversion, except `mp4a` whose `esds` object type is MP3 (`0x69`/`0x6B`). Files without MP4 headers do not count. A file that cannot be read (for example no read permission) does not count and is not saved, so the next check reads it again. Results go to the device-local `<data dir>/web-video-scan/<game id>.json` (`{version, root, files: {path: {size, mtime_ns, needs}}, play_anyway, other_roots}`, written through a temporary file and `os.replace`). Only new files and files whose size or mtime changed are read again; a changed root (a moved game, or an alternate launch target in another folder) starts a new file list. The "Play anyway" fingerprint of the previous root moves to `other_roots` (at most 16 folders, newest kept), and it comes back when that root is checked again. The file is deleted when the game is removed and is never exported or synced. When files need conversion and `play_anyway` does not equal the SHA-256 fingerprint of the sorted `(path, size, mtime_ns)` of those files, the launch returns `{success: false, code: "web_media_unsupported", error, media: {count, ffmpeg}}` and the player does not start. A failed check never blocks the launch.
- **Video conversion (`core/api_mixins/web_media.py`)**: `start_web_media_conversion(game_id)`, `cancel_web_media_conversion(game_id)`, `get_web_media_conversion_status(game_id)` (`{running, finished, done, total, current, converted, failed, failed_files, cancelled, error}`; the last finished job stays readable) and `set_web_media_play_anyway(game_id)` (saves the current fingerprint). `ffmpeg_info()` finds `ffmpeg` and `ffprobe` through `host_which` and parses `ffmpeg -encoders` once per run, and again at each launch check while no usable ffmpeg was found (start always refreshes it): video `libsvtav1`, else `libvpx-vp9`; audio `libopus` is required. `media.ffmpeg` has `available`, the encoders, `reason` (`missing`, `no_video_encoder`, `no_audio_encoder`) and `install` (`winget install Gyan.FFmpeg` on Windows, the NixOS line, or the first Linux package manager found; `host: true` in the Flatpak). Start refuses a game that runs, is busy, or when another conversion runs (one job at a time, one ffmpeg at a time), and refuses Flatpak document-portal folders (`/run/user/*/doc/`). The job deletes leftover `*.wlib-partial` files, then for each file: checks free space (source size + 64 MiB, else it stops with an error that names the mount point), encodes to `<name>.wlib-partial` with `-f mp4 -movflags +faststart` (SVT-AV1 `-preset 8 -crf 35` or VP9 realtime `-crf 33`, Opus 96k; `-map 0:V? -map 0:a?` leaves out cover art; `-map 0:s? -c:s copy` keeps subtitle tracks, and a track MP4 cannot hold fails the file; streams that are already AV1/VP9 or Opus/MP3/FLAC are copied), checks the output with `ffprobe` (cover art, `disposition.attached_pic`, does not count as video; same stream kinds, the same number of subtitle tracks, supported codecs, duration within max(0.5 s, 2 %)), checks that the original still has the same device, inode, size and mtime (a file that changed while ffmpeg ran, for example an update, is kept and counts as failed), copies the mode bits and `os.replace`s the original, then records the new size and mtime as `needs: false`. A failed file keeps its original. When the first three files all fail, the job stops (ffmpeg older than 4.3 cannot write Opus in MP4). Cancel stops after the current file. In the Flatpak, ffmpeg runs through `host_command`. When wLib quits, `_web_media_shutdown` kills ffmpeg and deletes the partial file. While a job runs, `_game_files_busy_reason` returns `WEB_MEDIA_BUSY`, so launch, move, uninstall, mod tools and save restores refuse the game; `Api.launch_game` reports it as `code: "web_media_converting"` (also when the launcher's reservation catches it) so the UI opens the progress dialog.
- **Launch Targets**: Alternate targets reuse the same launcher entrypoint as the default executable; only the selected executable path changes. Playtime remains keyed to the parent `game_id`.
- **Wine & Proton**: Plain Wine launches prepend the configured `wine` binary with the target's `WINEPREFIX`. Proton launches execute through `umu-run` (with the shared Steam Linux Runtime container) via `core/umu.py` and `core/umu_launch_wrapper.py`. Direct invocation of `proton run` is deprecated because modern Proton builds require the runtime container. If umu-launcher or the required runtime is missing, launches are refused with `umu_missing` or `umu_runtime_missing`. Existing Proton compatibility directories (`proton_compat`) are preserved, and symlinked `pfx` targets that umu would overwrite are rejected.
- **Network Isolation**: When `block_network` is enabled, Linux launches execute inside a private network namespace with only a loopback interface (`--unshare-net` inside bubblewrap sandbox, or a thin root-loopback `bwrap` wrapper when unsandboxed). A missing or unusable bubblewrap refuses launch with `network_block_unavailable`; on Windows, network isolation requires Sandboxie (`network_block_needs_sandbox`), and the box sets `NotifyInternetAccessDenied=n` so a blocked game does not open Sandboxie's SBIE1307 message window. For offline launches, Proton runner codenames are resolved to an installed build before launch, refusing with `proton_missing_offline` if none exists. The umu launch wrapper skips rewriting the runtime install marker so read-only mounts in the sandbox do not fail.
- **Cheat Engine Integration (Linux)**: Starts `lunarengine-x86_64.exe` through Wine/Proton, passing a Lua injection script to map directly to the game's PID. Sandboxed Proton launches skip Cheat Engine injection, while unsandboxed Proton launches join the running game's container.
- **Download Verification**: GE-Proton tarballs are checked against the release's `.sha512sum` asset (releases without one are refused). The Lunar Engine zip must match the pinned `LUNAR_ENGINE_SHA256` in `core/api_mixins/runtimes.py`; update it together with the download URL.
- **Update Checks**: `check_app_updates()` caches a successful GitHub release lookup for the session (GitHub allows 60 anonymous API calls an hour). Bulk game checks save `last_update_check` only after a run finishes without being cancelled, so a run cut short is retried at the next startup.
- **RPGMaker Tooling**: Implements enhanced Wine/NW.js fixes for RPGMaker MV/MZ and launches supported RPG Maker XP, VX, VX Ace, MV, and MZ games through the external `rpgmakermlinux-cicpoffs` runner in `rpgmaker_linux` mode or automatically in Linux `auto` mode when the runner (and `mkxp-z` for XP/VX/VX Ace) is installed and no Wine-specific setting (`auto_inject_ce`, `custom_prefix`, or per-game `proton_version`) is active. `core/rpgmaker_runner.py` owns `runner_install_dir()` (`~/.config/defrpgmakerlinuxpath.txt` or `~/desktopapps`), `mkxpz_status()` (`<install dir>/mkxp-z/mkxp-z.<machine>`), `runner_engine()`, and `resolve_auto_runtime()`. Installs run only on a click in Settings: `install_rpgmaker_linux_runner()` downloads the pinned runner tarball (`RUNNER_VERSION`), checks its SHA-256 and runs the upstream `install.sh` on the host; `install_rpgmaker_mkxpz()` (needs the runner) unpacks the pinned mkxp-z zip itself, keeps the exec bits and points `mkxp.json` at the install folder. Both run on one background thread; `get_rpgmaker_runner_install_status()` returns `{running, target, stage, done, total, error}`, and a second install while one runs is refused. wLib never runs upstream update, export, bug-report, patching, or plugin-install commands on the user's behalf.
- **NW.js bundles (Linux)**: A native launch whose game folder holds `libnw.so` (in the folder or its `lib/` subfolder) gets `GLIBC_TUNABLES=glibc.rtld.execstack=2` appended and, outside the sandbox, `XDG_CACHE_HOME` pointed at `<cache root>/wLib/nwjs/build-<size of libnw.so>` (`core/nwjs_compat.py`). Old NW.js builds abort at startup otherwise: glibc 2.41+ refuses their `libnode.so`, which asks for an executable stack (the tunable's value `2` needs glibc 2.42+), and their built-in fontconfig finds no font in a cache written by a current fontconfig. An `XDG_CACHE_HOME` in the launch options wins, other tunables in the launch options or wLib's environment are kept with `execstack=2` added beside them (an existing `execstack` entry wins), and a sandboxed game keeps its own private cache. Each NW.js build gets its own cache folder because an old build's fontconfig aborts on a font cache that a newer build wrote (NW.js 0.29 after 0.48), and that cache stays bad. A build with no `libEGL.so` beside `libnw.so` (no ANGLE, such as NW.js 0.29 / Chromium 65) is also started with `--use-gl=desktop`: without it Chromium falls back to SwiftShader, which draws the game on the CPU (low FPS, slow text), instead of using Mesa. Builds with `libEGL.so` already use the GPU, and from Chromium 110 (NW.js 0.73) `--use-gl=desktop` forces SwiftShader or turns WebGL off, so they get no flag. A `--use-gl`, `--use-angle`, `--disable-gpu` or `--in-process-gpu` argument in the launch options replaces it.
- **Playtime Tracking**: The launcher's watcher reports approximately 60-second ticks and a final exit/shutdown tick. `Api.launch_game` captures the installed version before launching, creates one session on success, and buffers any ticks that arrive before the launch returns. `record_play_tick(game_id, session_id, delta, is_final)` updates total playtime, session duration, and final `ended_at` in one transaction. Normalized session durations for the launch-time version accumulate toward 300 seconds, then set `last_played_version`; empty versions never set it. Changing the installed version mid-run keeps the session on its original version. System-browser HTML targets return `tracks_playtime: false` and create no journal session; built-in player launches are tracked like any process.
- **Journal bridge**: `get_game_play_sessions(game_id)` returns `{success: true, sessions: [...]}` or `{success: false, error: ...}`. `wlib-playtime-tick` keeps its name and reports `{gameId, delta, isFinal, lastPlayedVersion, sessionId}`. The library updates playtime and the Unplayed badge; the open Journal refreshes its sessions. Interrupted sessions remain without an end time. If the open session disappears mid-play (sync pull or import) or cannot be created, ticks still add to `playtime_seconds`.
- **Skipped releases.** The rules in `core/versions.py` hide a latest version that matches the skipped release, matches the installed release under a different spelling, or is lower than the installed version. A different latest version with no clear order can still count as an update. When F95 and LewdCorner both have a version, the higher version wins and post times decide unordered pairs. Matching spellings keep the F95 text and mark the release available on both sites. Single and bulk checks still store latest metadata and report `skipped`. `update_game` clears a skip when the normalized installed version changes.
- **Refresh F95 info option**: `check_all_updates(game_ids=None, refresh_info=False)` accepts `refresh_info` (bridge positional arg, sent by `checkAllUpdates(ids, { refreshInfo: true })`). A refresh pass only queues games with an F95 URL (catalog-only Ryuu games are skipped) and, for each game, reads the thread once through the shared scraper throttle (reusing a read the version check already made). From that one read it stores the F95 rating (`_store_f95_rating_for_url`), and `_refresh_f95_info_for_url` overwrites `cover_image_path` only when the thread cover is non-empty and different (then wakes `cover_cache`) and merges the thread's tags with the user's tag changes through `core/f95_tags.merge_f95_tags` (one `UPDATE` per game, `f95_tags` becomes the thread's list, `user_f95_tags` is read as the kept user tags and becomes the user-added tags that the thread lists, `tags_user_edited` never changes). Automatic backfill fills empty covers. It can merge thread tags into a recorded empty F95 tag list after a user edit. `get_update_status` reports `refresh_info`, and each result entry of a refresh pass adds `info_changed` (cover, rating or tags changed) and `previous` (the old values of only the changed fields among `cover_image_path`, `rating`, `rating_count`, `rating_updated_at`, `tags`, `f95_tags` and `user_f95_tags`; an old NULL `user_f95_tags` is reported as `''`) so the UI can offer one Undo through `update_game`. A cancelled pass keeps the results it already wrote. A failed thread read keeps the existing info.
- **F95 tags in ordinary bulk checks**. A bulk check fills tags only for checked games with a recorded empty F95 tag list. It uses the thread page read for the game, then a page fallback result, or the local catalog when the check has no page data. The fill makes no extra F95 requests. It puts thread tags first, keeps current tags, and stores the thread tags as the new baseline.
- **Thread On Hold and Abandoned states**: `f95zone.thread_prefix_flags` reads `completed`, `onhold` and `abandoned` from prefix labels (no case, spaces or punctuation, so F95 `Onhold` and LC `On Hold` match). `scraper._extract_page`, `lewdcorner.prefix_details` (which takes `LcPrefix(name, id)` items and skips id 29 for the engine) and `game_lookup._catalog_thread_entries` give `thread_onhold` and `thread_abandoned` (catalog entries give `None` without named prefixes); `combined_thread_entry` keeps F95's values when they are not `None`. The write sites are `database.store_thread_update(states=...)` (used by `lewdcorner_updates.store_f95_version` with the F95 catalog entry and by the LC check), `_update_thread_edit_metadata_for_url` (page reads), the catalog fill, `add_game` and the archive install. The LC check writes states only for a game without an F95 thread; for a game on both sites `database.site_thread_states` lets the LC states (`CheckResult.states`) apply only when the F95 catalog has no prefix data and the game's states are still unknown, and a page read always wins over the catalog. Catalog entries carry `thread_states_seen_at` (the builder's `last_seen`); `database.thread_state_fields` ignores catalog states that are not newer than the game's `thread_states_at`, and records the read time of every state it writes. It also decides `newly_abandoned`: the stored value goes from `0` to `1` on a game that is not Archived. `add_game` and the archive install take caller states through `database.caller_thread_states`: LC page states (no `thread_states_seen_at`) apply with the time now only to an LC-only game; catalog states keep their `thread_states_seen_at`. Bulk results and `check_for_updates` return `newly_abandoned` next to `newly_finished`. The catalog fill keeps the games it finds newly abandoned in a list that `take_abandoned_notices()` empties; `App.vue` calls it on each update status poll and shows a toast (no desktop notification).
- **Archived games and update checks**: `check_all_updates` leaves out games with the `Archived` play status (`database.is_archived`) on three library-wide paths: a check with no `game_ids` (Updates page "Check All Games"), an `automatic=True` check, and a check with the keyword-only `skip_archived=True` (both calls in `core/api_mixins/sync.py`). They are not counted in `total` and get no F95 or LC request; a check with no `game_ids` still stores the LC feed items it already read for them (`lewdcorner_updates.store_feed_item`), so the saved feed cursor does not hide those items. A check for chosen ids (per-game check, library bulk actions, Updates page selection) still checks them. `_version_check_fields` returns `has_update: False` and `archived: True` for an Archived game, so it never counts as a new update in the notification; `hasAvailableUpdate()` in the UI uses the same rule.
- **Desktop notifications**: `maybe_auto_check` calls `check_all_updates(automatic=True)`; the keyword is internal to Python. An uncancelled run sends at most one Linux notification for changed latest versions that now have updates, plus newly completed wishlist games. Automatic runs qualify; manual runs qualify when the window is unfocused at completion. `set_window_focused(focused)` defaults to focused, and App reports focus, blur, and visibility changes. Updates > Automatic Checking has the default-on Desktop notifications toggle, saved as general setting `update_notifications` (`on`/`off`). The sender uses a daemon thread, `notify-send` then `gdbus`, five-second subprocess timeouts, and swallowed/logged failures. Flatpak permits the notification service. No new Python dependencies or Windows notifications.
- **Running Registry**: `launch(..., game_id=...)` registers process handles under a lock and removes them on exit by process identity before the final playtime tick. Linux launches use a new session; Stop sends SIGTERM to the process group and SIGKILL after five seconds if the group remains. Wine/Proton also uses the matching `wineserver -k` with the resolved prefix when available (Proton `files/bin` or `dist/bin`, Wine sibling or system server). This ends all processes in that Wine prefix, so it is skipped while another tracked game uses the same prefix (that game keeps running; only the stopped game's process group is signalled). Windows starts each unsandboxed game suspended inside a Job Object (no kill-on-close, so games outlive wLib), so a launcher that starts the real game and exits stays tracked while game processes remain in the job, and Stop ends those processes. Shared programs a game starts (a browser for a link, the Steam client, `conhost.exe`, `WerFault.exe`) neither keep the game running nor get closed by Stop. Elevated games (UAC) and a refused job fall back to `taskkill /T /F /PID`; failure advises closing the game itself. 7-Zip on Windows runs with `-sccUTF-8` (dropped for builds that reject it) so non-ASCII names list correctly. Helper tools (7-Zip, SbieIni, taskkill, powershell, winget) run with `CREATE_NO_WINDOW` because the windowed Windows build would otherwise open a terminal for each.

### `core/scraper.py` (HTTP Scraping)

- **Batch Versions**: `check_versions(urls, callback)` requests `https://f95zone.to/sam/checker.php?threads=<ids>` with at most 100 unique thread IDs per request. Versions use the title parser shared with the extension before comparison.
- **Page Fallback**: Missing, empty, and non-actionable versions, or endpoint failures other than challenges and HTTP 429 rate limits, fall back to guest thread pages. Regex extraction reads the title and starter post.
- **Guest-hidden attachments and links**: When a plain-HTTP page's starter post hides links, or hides attachments and the catalog has no cover, `_get_page()` re-fetches that thread once through a connected extension to get the signed-in HTML, because guest requests see a login prompt instead of screenshots posted as attachments or store links. The guest page is kept when no extension is available, the extension response is not HTTP 200, or that response is challenged or login-gated. This applies only to single-thread page reads; batch endpoint reads do not load the thread page.
- **Metadata**: Add-game fetches and single-game checks read engine, tags, cover, screenshots, store links, the thread's Completed flag, and starter-post edit timestamps. Thread page reads refresh screenshots alongside thread edit metadata: `_update_thread_edit_metadata_for_url` replaces the stored list when the page carries a non-empty screenshot list and keeps the stored list on an empty result. Bulk checks from the batch endpoint do not read the thread page and leave screenshots unchanged; bulk wishlist/fallback paths that read the thread page store them. A screenshots-only refresh does not bump `sync_local_modified_at`. Bulk checks preserve stored edit metadata.
- **Extension fallback order**: `_fetch_with_fallback(url)` is used by `_get_page` and `_check_chunk`. It tries plain HTTP first, then on `blocked` or `login_required` retries the same URL once through the connected extension (`core/extension_bridge.py`). The extension body is re-classified with the same rules; error results carry `browser_fallback: "unavailable"` (no eligible extension), `"logged_out"` (the extension returned F95's login page, so the browser sent no F95 login with its request), or `"failed"` (extension also challenged or its fetch failed). Each extension fetch reads XenForo's `data-logged-in` flag and passes it to `extension_bridge.record_fetch_outcome`; `extension_bridge.status_snapshot()` (connection state, disconnect count, last fetch) appears under the extension in Diagnostics, and bridge connects, disconnects and login-state changes go to the app log. No fallback runs for `rate_limited`, `not_found`, timeouts, or network errors. A challenged batch retries the same batch URL once through the extension, never as 100 thread pages.
- **Extension-first window**: a plain-HTTP `blocked` result sets `_prefer_extension_until = now + 15 minutes` (in memory only, never persisted). While the window is active and `extension_bridge.is_available()` is true, requests go straight to `_f95_get_via_extension` without a plain-HTTP attempt; its classified result is final. With no eligible extension connected, the window is ignored and plain HTTP is used. `login_required` never opens the window.
- **Pacing and TLS**: Every request passes through `_run_paced_f95_request`, which holds the global `_F95_REQUEST_LOCK` through the request and waits after the previous request finishes, for both `_f95_get` (urllib) and `_f95_get_via_extension` (bridge). `WLIB_UPDATE_CHECK_DELAY_SECONDS` defaults to 2 seconds and is bounded to 1–30. urllib uses the default SSL context and the configured CA certificates. Extension fetches count as F95 requests for serialization and pacing: no plain HTTP request runs while an extension request is pending, and consecutive requests stay spaced by at least the minimum interval.
- **Bounds and guarantees**: wLib waits at most 30 seconds for an extension response and never waits for an extension to connect. The fallback never opens a browser window or tab and never starts a browser; it works only when the user's browser is already running with the extension.
- **Failures**: Deleted threads report `not_found`, challenges report `blocked`, and login walls report `login_required`. Network timeouts report `navigation_timeout`; other network or parse failures report `scraper_error`.
- **F95 rating**: `_extract_page` returns `rating` (float) and `rating_count` (text, such as "120 reviews") only when the page has a rating above 0. It reads the selectors the extension uses: the signed-in banner ring `.f95rv-banner-ring[aria-label]` ("4.6 out of 5"), the guest stars `.f95rv-banner-stars .f95rv-stars[aria-label]` ("4.6 stars"), the count from `.f95rv-banner-count`, and the older `.br-widget.bratr-rating` star widget as a fallback. Every page read stores it through `ApiBase._store_f95_rating_for_url` as `rating = "X.X/5 (count)"` (or `"X.X/5"` when no readable positive count is present), `rating_count` = the parsed positive integer (or `NULL`), and `rating_updated_at` = the read time (UTC ISO), for each game with that thread: single checks (`check_for_updates`), bulk page-fallback and wishlist metadata reads, and Refresh F95 info. A page with no rating keeps the stored rating and count. The installed catalog is the second source (see the Game catalog client section); a catalog rating never replaces a newer page read.
- **Callbacks**: Results are delivered in input order, shared thread IDs reuse results, returning `False` stops processing, and callback exceptions propagate to the update worker.

Run `ruff format .` before you commit; the checks run `ruff format --check .` and fail on unformatted files. When the formatter splits a line, keep a `# noqa` comment on the line that Ruff reports. Use `# fmt: off` / `# fmt: on` only for data that is easier to read with manual alignment. Commits that only reformat go in `.git-blame-ignore-revs`.
- **Local checks**: Linux wrappers `bash scripts/check-python.sh` and `bash scripts/check-python-clean.sh` run `ruff check`, `ruff format --check`, `basedpyright`, the smoke check, and `pytest` in an active or fresh Python 3.12 environment. ## Locale Emulator (Windows)

`core/locale_emulator.py` finds Locale Emulator's `LEProc.exe` and builds the
command that starts a game through it. wLib does not download or install it.
`get_status(custom_path=None, *, platform=None, recheck=False)` returns
`{status, path, reason}` with `ready`, `missing` or `unusable`. On a host that
is not Windows it is always `unusable`. The detection order is:

1. The `locale_emulator_path` setting. A saved path is used alone: when the file
   does not exist the status is `missing` and the reason names the path. A file
   name that is not `LEProc.exe` (case-insensitive) is `unusable`.
2. The folder that `LEInstaller.exe` records:
   `Software\Classes\CLSID\{C52B9871-E5E9-41FD-B84D-C5ACADBEC7AE}\InprocServer32`
   value `CodeBase` (a `file:///` URL of `LEContextMenuHandler.dll`), in HKCU
   (per-user install) then HKLM (all users), 64-bit view. `LEProc.exe` must
   exist in that folder.
3. `%ProgramFiles%\Locale Emulator\LEProc.exe`, then
   `%ProgramFiles(x86)%\Locale Emulator\LEProc.exe`.

Only a `ready` result is cached; `recheck=True` clears the cache. The bridge
methods are `get_locale_emulator_status()` and
`recheck_locale_emulator_status()` in `core/api_mixins/launch.py`. Settings
picks the file with the generic `browse_file()`.

`locale_emulator_path` is a string setting with the default `''`. `save_settings`
refuses a value that is not a string, and a non-blank value whose file name is
not `LEProc.exe`, with "Choose the Locale Emulator LEProc.exe executable.". It
is in `PATH_SETTINGS_KEYS`, so library export writes it in the path group, sync
does not carry it, and import skips it with a `foreign_path` warning on a host
where it is not a valid path (a Windows path on Linux). The platform capability
`japanese_locale` is true on Linux and Windows.

## Game sandboxing

`core/game_sandbox.py` owns cached host detection, argv construction, Sandboxie
configuration, process-list parsing and tool installation. Linux detection runs
host `bwrap --version`, then a namespace probe with the launch options; Flatpak
runs both through `host_command`. `ready`, `missing` and `unusable` include a
path, version and reason. Only successful probes are cached, so a missing or
unusable tool is checked again next time; Recheck also clears the cache. Platform
capabilities expose `sandbox` (`bwrap`, `sandboxie`, or null).

The launcher wraps the final mode-specific argv before `host_command`. bwrap
uses private user/PID/IPC/UTS namespaces, a private `/tmp` and `/run`, read-only
system and runtime mounts, selected display/audio sockets, a writable game
folder and Wine prefix, and `<data dir>/sandbox/<id>/home` at the real HOME
path. A sandboxed Wine/Proton game without a custom prefix (or a `WINEPREFIX=`
launch argument) runs in its own prefix, `<data dir>/sandbox/<id>/prefix`
(`game_sandbox.sandbox_wine_prefix`), never the global one: the prefix is
writable inside the sandbox, so sharing it would let the game plant DLLs or
registry entries that later run unsandboxed in other games. Save detection and
the game's Winecfg, Winetricks and RTP actions resolve the same prefix. Removing a game moves its `sandbox/<id>/` folder to `sandbox/removed/<id>_<timestamp>/`, so a later game with the same ID starts clean; startup deletes removed sandboxes older than 30 days. On non-NixOS hosts, `/bin`, `/sbin` and `/lib*` entries that are symlinks
on the host are recreated as symlinks, so 32-bit loaders resolve, and
`/dev/ntsync` is passed through when present. It does not expose the session
D-Bus: `DBUS_SESSION_BUS_ADDRESS` is set to an unusable path
(`unix:path=/run/wlib-no-session-bus`) and `NO_AT_BRIDGE=1` is set, so libdbus
and GTK's accessibility bridge get a connection error instead of starting a
private bus that never exits. `/tmp/.X11-unix` is a new folder that the sandbox
user owns, with only the host's X display sockets (`X<n>`, listed on the host
by `host_platform.host_x11_sockets()`, also in Flatpak) bound in read-only, so
nested X servers such as gamescope or Xvfb can create their own display. The game gets a filtered environment (`game_sandbox.sandbox_environment`):
display, audio, locale, graphics and Wine/Proton variables from the host plus
everything wLib or the launch options set, but none of wLib's other variables
(tokens, SSH/GPG agents, credentials). bwrap runs without `--die-with-parent`,
so a sandboxed game keeps running when wLib quits, like other games. An in-namespace shell supervises launcher stubs until their detached
descendants exit. It ignores D-Bus and accessibility bus helpers
(`dbus-daemon`, `dbus-launch`, `dbus-broker`, `at-spi-bus-launcher`,
`at-spi2-registryd`) when it counts processes, and kills every process left in
the sandbox's PID namespace before it exits, because bwrap's init otherwise
waits for those helpers. Stop terminates the outer bwrap process group and skips the
host wineserver. Automatic Cheat Engine injection, when enabled, runs inside
that same sandbox after its usual delay. A sandboxed RPGMaker Linux runner
launch starts the runner by its real path (`os.path.realpath`), because the
sandbox mounts only the runner's real folder (`game_sandbox.runtime_folder()`)
and a symlink such as `~/.local/bin/rpgmaker-linux` does not exist there.
Because the upstream runner replaces `www`, `package.json` and root-file
symlinks inside its NW.js version folder on each launch, `build_bwrap_argv`
mounts that `runner_root` (checked with `check_readonly_mounts` after
`readonly_paths`) through `game_sandbox.runner_root_mounts()`: when
`game_sandbox.runner_overlay_supported(bwrap, root)` succeeds (probed through
`host_command` on the real runner root, cached by `(bwrap, root)` and cleared
by `get_sandbox_status(recheck=True)`), it uses `--overlay-src <root> --tmp-overlay <root>`
so writes stay private to the sandbox and disappear on exit; when overlayfs is
unavailable (logged once), it falls back to `--ro-bind <root> <root>` plus a
`--tmpfs` over each `<root>/nwjs/<version>` folder with every non-symlink entry
other than `www` and `package.json` bound back read-only. The tmpfs mounts give every
version folder the same new modification time, so in the fallback
`game_sandbox.runner_fallback_nwjs_path()` sets `NWJSPATH` to the folder the
runner picks on the host (newest by modification time, like its `ls -t`), unless
the command has `--nwjsversion`, `--chooselatestnwjs` or `--nwjspath` or the
environment already sets `NWJSPATH` (the runner refuses those together). When
`runner_root` is set, `build_bwrap_argv` also checks `runner_install_dir()` and
`<install dir>/mkxp-z` with `check_readonly_mounts`, binds the host's
`~/.config/defrpgmakerlinuxpath.txt` read-only at the same path after the
sandbox-home bind when that file exists, and mounts `<install dir>/mkxp-z` with
`--overlay-src <mkxpz_dir> --tmp-overlay <mkxpz_dir>` when that folder exists
and `runner_overlay_supported(bwrap, mkxpz_dir)` succeeds so the runner's
per-launch `mkxp.json` edit stays private to the sandbox. Because the sandbox
exposes no FUSE device, a sandboxed runner launch whose final argv (after
`%command%` substitution) selects `--mounttype cicpoffs` is refused before any
process starts with `code: "rpgmaker_cicpoffs_sandbox"` (unsandboxed launches
keep `--mounttype cicpoffs`). Likewise, a sandboxed RPGMaker Linux launch of an
XP, VX or VX Ace game (`runner_engine == "mkxpz"`) when
`runner_overlay_supported(bwrap, mkxpz_dir)` is false is refused before any
process starts with `code: "rpgmaker_mkxpz_sandbox"` (MV/MZ keep the read-only
fallback).
A sandboxed plain Wine launch with an absolute Wine path does the same for its
binary path: the game and Cheat Engine run the Wine target, not a symlink such
as `~/.local/bin/wine`. The supervisor first writes `.wlib-sandbox-started` in the
sandbox home (`game_sandbox.SANDBOX_STARTED_NAME`; the launcher deletes it before
each launch). When bwrap exits with a nonzero status before that file appears
(checked for up to five seconds), the launch fails instead of starting playtime
tracking: a fresh bubblewrap check (`recheck=True`) gives `sandbox_missing` or
`sandbox_unusable` with its reason, otherwise the error names the exit status.

When MangoHud is in effect for a sandboxed launch (wLib adds the `mangohud`
wrapper, the user's arguments before `%command%` start `mangohud`, or the launch
environment sets `MANGOHUD=1`), `game_sandbox.mangohud_mounts()` adds
`--ro-bind-try` pairs after the sandbox-home bind and the runtime mounts:
`/sys/class/drm` (MangoHud aborts without it), `/sys/class/hwmon` and
`/sys/class/power_supply`; the host's MangoHud configuration folder
(`$HOST_XDG_CONFIG_HOME/MangoHud` in Flatpak, else `$XDG_CONFIG_HOME/MangoHud`,
else `~/.config/MangoHud`, bound by real path) at the sandbox's
`~/.config/MangoHud`; and the files named by `MANGOHUD_CONFIGFILE` and
`MANGOHUD_PRESETSFILE` (absolute values only) at the path the variable names.
Every source goes through `check_readonly_mounts`, so a configuration path whose
real path would show HOME or wLib's data folder refuses the launch. Launches
without MangoHud get none of these paths.

No internet adds `--unshare-net` to the sandbox. With sandboxing off it uses a
thin `bwrap --unshare-user --unshare-net --dev-bind / /` wrapper with the
original working directory. Only `/tmp/.X11-unix` is private: a tmpfs that the
namespace user owns, with the host's X display sockets bound in, so nested X
servers can start (the host folder belongs to root, which shows as `nobody` in
the user namespace). Files, Stop, playtime and the host wineserver
behave as unsandboxed; only a private loopback remains. Wine companion tools and
automatic Cheat Engine injection for that game run in the same kind of wrapper,
so they stay offline too. A missing or unusable
bubblewrap refuses the launch with `network_block_unavailable`; Windows requires
the sandbox (`network_block_needs_sandbox`). A network-blocked game cannot share a Wine prefix with a running game that has
network (or the other way round): processes on a shared wineserver outlive one
game's block. Proton codenames resolve to
installed builds before offline launches, otherwise `proton_missing_offline`
refuses the launch. Offline, umu rewrites its runtime install marker; the launch
wrapper skips that when the marker already exists, because the sandbox mounts
the shared runtime read-only.

Windows configures `wLib_<id>` with `SbieIni.exe set` and `/reload`, preserving
sandbox storage and replacing the game-folder pass-through path each launch.
Tracking parses the count followed by PIDs from `Start.exe /box:<box> /listpids`;
Stop calls `/terminate` in the game's Windows session. HTML games continue to
open in the browser without sandboxing or playtime tracking. A missing or
unusable tool refuses a sandboxed launch; it never falls back to a plain launch.
A writable mount (game folder, Wine prefix, or Sandboxie pass-through path) that
is `/`, HOME, or an ancestor of HOME is refused, because it would expose the whole
home folder. A runtime under `~/.local/bin` mounts only that `bin` folder.

Each running Wine/Proton game records its resolved prefix and sandbox mode.
Under the registry lock, a launch is refused with `prefix_in_use` when the same
prefix is already in use and either launch is sandboxed. Prefix comparisons
resolve symlinks and normalize Proton's `pfx` subdirectory. The error names the
running game. The API reads sandbox preferences from the stored parent game,
including launches through extra targets.

Frontend-callable sandbox methods:

| Method | Result / behavior |
| --- | --- |
| `get_sandbox_status()` | Cached tool status, path, version and reason. |
| `recheck_sandbox_status()` | Re-runs host detection. |
| `get_sandbox_install_info()` | Host command, package manager, pkexec availability, install availability and official URL. |
| `install_sandbox_tool(tool)` | Starts a background install; mismatched host/tool returns `unsupported_platform`. |
| `get_sandbox_install_status()` | Thread-safe running/done/current/error progress. |
| `set_sandbox_for_all_games(enabled)` | Updates every game's next-launch preference and returns `changed`. |
| `open_game_sandbox_folder(game_id)` | Opens persistent per-game storage, creating the folder if necessary. |

Linux installs use the distro's bubblewrap package via host `pkexec`; no portable
bwrap is downloaded. Windows installs prefer winget. The direct-download
fallback selects the official architecture-specific GitHub release, checks
Authenticode trust and the expected publisher before elevation, and deletes the
staged installer on every exit. Signature failure never runs the installer.

Save detection searches both the real profile and the sandbox profile when the
stored flag is enabled: Linux `.renpy`, `.config` and `.local/share`, and Windows
box `user/current`/profile roots with AppData, Documents and Saved Games. Overrides
continue to work when sandboxing is switched off. Removing a game or switching
sandboxing off does not delete its sandbox storage. JSON backups carry the
preference and selected settings, while sandbox files remain local.


## Proton and umu-launcher

Upstream Proton builds require the Steam Linux Runtime container (`sniper` or
`steamrt4`). `core/umu.py` manages `umu-launcher` (`umu-run`) on Linux so Proton
games, Wine companion tools, Cheat Engine, and prefix/RTP/Winetricks installers
execute inside the proper container environment.

- **Discovery**: `locate_umu()` checks for system `umu-run` on `PATH` via
  `host_which("umu-run")`, falling back to wLib's downloaded copy under
  `<data dir>/umu/umu-run`. `get_umu_status()` reports path, source (`system` or
  `wlib`), version string, and whether `python3` is available on the host.
- **Zipapp download**: `download_release()` and the `UmuDownload` worker fetch
  the latest verified zipapp from the GitHub release
  (`Open-Wine-Components/umu-launcher`). The download verifies SHA-256 and SHA-512
  checksums, ensures member paths stay safe, and extracts only the single
  executable member `umu/umu-run` into `<data dir>/umu/umu-run` (capped at 8 MiB)
  with mode 0755.
- **Steam Linux Runtime**: Runtimes reside in `~/.local/share/umu/<variant>`
  (`XDG_DATA_HOME/umu`), where the variant comes from the build's
  `toolmanifest.vdf` `require_tool_appid` (`steamrt3` for sniper, `steamrt4`).
  Like umu 1.4.1+, `GE-Proton`/`UMU-Proton` codenames (and an empty runner, which
  umu treats as UMU-Proton) resolve to the newest installed build before reading
  its manifest. A runner that is not a Proton build, such as plain Wine, launches
  and prepares with umu's UMU-Proton default, so its runtime status follows the
  UMU-Proton build too. `runtime_status(runner)` checks for `.installed.ok` or
  `_v2-entry-point` plus platform directories. `UmuRuntimePrepare` runs
  `umu-run createprefix` in the background with `GAMEID=umu-default` and the
  selected runner's `PROTONPATH`. The UI polls status and progress (installed folder
  size in MiB), and supports cancellation via SIGTERM/SIGKILL to the process group.
  Failures classify into `disk`, `network`, `python`, or `other`, alongside raw
  stderr log tails or a message naming any Proton manifest with invalid UTF-8.
- **Invocation construction**: `build_umu_invocation()` produces
  `["python3", "<data dir>/umu/umu-run-wlib", executable]` with environment:
  `WINEPREFIX` pointing to `proton_compat`, `GAMEID` set to `umu-wlib<id>` for
  tracked games or `umu-default` for installers, `PROTONPATH` set for custom
  runners and omitted for UMU-Proton, `STEAM_COMPAT_INSTALL_PATH` set to the game
  directory, and `UMU_RUNTIME_UPDATE="0"`. When not sandboxed,
  `UMU_CONTAINER_NSENTER="1"` allows companion tools and Cheat Engine to join the
  running game's container. Launches are refused if the `pfx` symlink inside
  `proton_compat` points elsewhere and would be replaced by umu.
- **Launch wrapper (`core/umu_launch_wrapper.py`)**: A small script deployed to
  `<data dir>/umu/umu-run-wlib`. When `UMU_RUNTIME_UPDATE=0`, it patches umu's
  `setup_umu` and `write_install_marker` at runtime. Skipping the update request
  and preventing rewrite of an existing install marker allows umu to launch
  reliably when the runtime is mounted read-only (in bubblewrap sandboxes or
  offline launches).
- **Offline codename resolution**: Offline Proton launches resolve runner codenames
  (`GE-Proton`, `UMU-Proton`) to an installed build before launching; if no
  matching build is installed, launch is refused with `proton_missing_offline`.
- **Sandbox integration**: Sandboxed Proton launches mount the shared Steam Linux
  Runtime read-only, with a per-game writable working directory
  (`<data dir>/sandbox/<game id>/umu-var`) for umu's state. Cheat Engine injection
  is disabled for sandboxed Proton launches. Proton games sharing a prefix cannot
  run concurrently.


## Companion tools

The Linux-only `companion_tools` capability controls launching; CRUD remains available on other hosts so saved definitions survive. The bridge exposes:

- `list_companion_tools()`: ordered definitions in `{success, tools}`.
- `save_companion_tool(tool)`: create or update by optional ID; returns `{success, tool}`. Validates name, kind, executable file and parsed arguments/command.
- `delete_companion_tool(tool_id)`: removes the definition and cascading overrides.
- `get_game_companion_tools(game_id)`: definitions with effective `visible` and `overridden` flags.
- `set_game_companion_tool_override(game_id, tool_id, visible)`: boolean to override, null to reset.
- `list_launchable_companion_tools(game_id)`: visible tools supported by the current run; empty when not running.
- `launch_companion_tool(game_id, tool_id)`: rechecks host, existence, visibility and running state; errors name the tool, and duplicates return `tool_running`.

`RunningGame` captures the executable path and a copy of the final Wine/Proton command and environment. Only unsandboxed Wine/Proton runs have `wine_context`; changing settings during play does not change it. Arguments use `shlex.split` followed by per-token `%game_dir%` / `%game_exe%` expansion and leading `VAR=value` extraction. Wine and Native tools use their own folder; Command tools use the game folder. Host tools strip packaged-runtime and inherited Wine/Proton environment variables.

The launcher starts tools through `host_command` in separate sessions, records them in `_tools` under the running lock, and reaps them independently of game playtime. A tool never keeps a game marked running. On game exit or Stop, only that game's Wine tool groups receive SIGTERM followed by SIGKILL after two seconds; Native and Command tools keep running and are forgotten. Cleanup never uses wineserver to terminate tool groups, so another game sharing the prefix is spared. Tool signalling rejects non-integer IDs, IDs <= 1 and the launcher's own group. Shutdown leaves games and tools running; tests disable atexit registration for mocked launchers.

Backup inspection summarizes tool definitions and warns about malformed entries or foreign-host paths. On Linux, import skips definitions whose executable is not on this host; Windows keeps imported Linux definitions unchanged because tools only run on Linux. Import counts `companion_tools_updated` and `companion_tools_skipped`, imports definitions before games in the same transaction, and merges by case-insensitive name. Overwrite preserves local IDs and replaces game overrides only when their field is present. Fill-missing retains matching definitions and existing overrides. Missing files generate migration warnings; definitions with host-compatible paths can still be imported and edited on the destination.

## Playnite imports and local covers

`core/external_import.py` accepts `playnite`, using the dependency-free LiteDB 4
reader in `core/litedb.py`. Pick `games.db` with its sibling database files,
`database.json` and `files/` directory. On Windows, detection reads Playnite's
`config.json` DatabasePath, then the default AppData library. Linux requires a
picked or copied library. Database format 4 is supported. Close Playnite first:
journal files and sharing failures return `source_locked`. Only the seven
library collections are snapshotted, and add-on settings are never read.
Missing optional database files or expected collections in valid metadata
databases are empty lookups (statuses, companies, categories, tags, features,
genres). Unresolved references omit those fields and preserve local values in
both merge modes. The Game collection remains required, even if empty;
corrupt, encrypted, locked, and unsupported databases still fail validation.

Playnite links, F95 plugin versions and prefixes, completion status, notes,
collections, seconds of playtime, dates and user scores are translated into the
existing import pipeline. File play actions support install variables and extra
launch targets; foreign-OS paths are dropped. An F95 thread, adult store/catalog
link (DLsite, Fanza, VNDB, Ryuugames), or host executable qualifies a game for
import. Steam or itch.io alone does not.

`core/game_covers.py` recognizes JPEG, PNG, WebP, GIF and AVIF by content and
enforces 20 MiB before and during copying. AVIF detection inspects the complete
initial `ftyp` box (up to 64 KiB), including normal/extended lengths and `avif`
or `avis` major/compatible brands. Filename extensions are ignored, so AVIF
named `.png` is stored as `.avif`. This is type recognition rather than full
image decoding. Atomic, byte-preserving copies use UUID filenames under
`<data dir>/covers/`. `choose_game_cover(game_id)` opens the image picker;
`set_game_cover_file(game_id, path)` copies a chosen image, and
`clear_game_cover(game_id)` removes it. Successful set/clear responses include
`game`; cancelling the picker returns `cancelled: true`. Game payloads include
`cover_local_url` only when the file exists and the extension server is bound.
Replacement, removal and game deletion clean up the old file.
The read-only cover route serves AVIF as `image/avif` with `nosniff` and the
existing private immutable caching policy. The embedded browser decodes it
directly; no conversion dependency is needed. Undecodable images use the
existing remote-cover fallback.

External previews expose `covers` only when source games carry `cover_file`,
and report `covers_to_copy`. Invalid images become per-game warnings. Covers
copy inside the database import transaction, roll back on failure and remove
replaced files only after commit. Fill-missing keeps existing local covers.

export or sync, and F95 metadata refreshes leave them alone.


### Remote cover cache

`Api` owns `CoverCacheService` in `core/game_covers.py`. After the window's loaded event it sweeps orphan files and fills `<data dir>/covers/cache/` in one daemon thread. Remote images share local-cover content validation (JPEG, PNG, WebP, GIF, AVIF; 20 MiB maximum) and atomic random-name storage. `f95_get_bytes` uses bounded plain HTTP reads without extension fallback, sharing the global F95 request lock and interval with page requests. Foreground waiters take priority over further background acquisitions, and a background download starts only after one interval with no foreground request, so bulk checks and imports keep their turn. Failed URLs are skipped for the rest of the session.

The device-only `games.cover_cache` filename and `games.cover_cache_url` source URL are written only through dedicated database helpers. Guarded writes discard downloads if the source URL changed or the game was removed. Adds, edits, metadata checks, backup imports and sync pulls wake the service. API reads expose a localhost `cover_cache_url` only for a current source URL and an existing file while port 8183 is available. `/covers/cache/<random name>` serves immutable images without directory listing.

**LC covers and screenshots.** A cover URL on `lewdcorner.com` never uses `f95_get_bytes`: LC answers 403 without the user's LC login. `_fill` handles LC URLs after the F95 ones through `fetch_lc_image(url, background=True)`, which asks the browser extension (`extension_bridge.fetch_image`, see `docs/extension_api.md`) and checks status 200, an image type and a complete image. A copy is stored like an F95 one. While no connected extension reports `can_fetch_lc_images`, LC covers wait without a failure entry or a timer; `ApiBase` connects `extension_bridge.add_lc_images_listener` to `CoverCacheService.wake()`, so the pass runs when such an extension connects. Bad answers and the hourly limit use the same growing retry delay as other failures (15 minutes, doubling, at most a day), and the LC part of the pass stops at the hourly limit.

LC pacing shares one LC gate with LC update checks, thread reads and download resolution, so one LC request runs at a time. Foreground requests wait 2 seconds after the previous LC request and go before waiting background requests. Background image fetches wait 5 seconds after the previous LC request (outside the gate, so a foreground request is not held behind that wait) and stop at 120 fetches in a rolling hour (`LcImageLimitReached`).

**LC Plus detection (`core/lewdcorner_plus.py`).** The "LC Plus" setting (`lc_plus_mode`) is Auto, Yes or No. In Auto, wLib reads the tier from LC itself. `detect(trigger)` runs single-flight and does nothing (and sends no request) while "Use LewdCorner" is off, the mode is not Auto, the catalog is off or holds no LC threads, or no extension can fetch LC pages. It takes up to three candidates from `game_lookup.premium_lc_threads()` (catalog tier Premium, newest first; rows with `origin = 'import'` only after the rows read from LC's Plus listings) and reads each through `extension_bridge.fetch(url, site="lc", background=True)`: one LC request at a time with the normal LC gap, behind every foreground LC request. `lewdcorner.tier_signal(body, status)` gives `plus` for a signed-in `thread_view` page whose `data-container-key` forum is in `LC_PLUS_FORUMS` (Games+ 119, AI Games+ 213), `standard` for LC's signed-in 403 `error` page, and `None` for anything else (guest, login, challenge, 404, a thread in another forum). It stops at the first signal and stores `lc_plus_detected` and `lc_plus_detected_at`; when every page says nothing, it stores only the time and keeps the last tier. The page body is never logged. Triggers: saving "Use LewdCorner" on or the mode to Auto, `extension_bridge.add_lc_fetch_listener()` when a connection's `can_fetch_lc` turns true (only when the last detection is more than 24 hours old), each catalog install (`_on_catalog_installed`, with the same 24-hour rule, so an extension that connected before the first catalog held LC threads still gets a detection), and the bridge method `check_lc_plus()` ("Check now", which returns the new state, `checked_without_result`, or an error with `code` `lc_off`, `mode`, `no_catalog` or `no_extension`). LC thread pages that update checks (`lewdcorner_updates.check_thread`) and download links (`scraper._fetch_lc_thread_download_links`) already read also go to `note_thread_page()` with no extra request: in Auto, a Plus-forum page sets Plus, and a 403 page sets Standard only for a thread the catalog marks Premium. When the effective state turns on, the existing Plus fill (`_apply_lc_setting_change(turned_on=True)`) runs in the background. `get_settings()` returns `lc_plus` as the effective state, plus `lc_plus_mode`, `lc_plus_detected`, `lc_plus_detected_at` and `lc_plus_check` (`ready`, `no_extension` or `no_catalog`). The detected tier and its time are device-local.

`get_game_screenshots` uses the LC catalog list (`game_lookup.lc_thread_screenshots`) when the F95 catalog lists none and the game's LC thread is active. Each LC URL in the answer becomes `http://127.0.0.1:8183/lc-images/<key>`, where the key is 32 random hex characters made once per URL for this app session, for both `thumb` and `full`. `Api.lc_image_keys` keeps the last 500 `key -> URL` pairs in memory only. The disk copy is named by the first 32 hex characters of the URL's SHA-256 (`<hash>`), which is never part of the address: a local program that knows the URL cannot work out the key. `GET /lc-images/<key>` answers 404 with no request for a key it did not hand out; serves `covers/cache/lc-<hash>.<ext>` with the `/covers/cache/` headers when that copy exists; else fetches the image through the extension (foreground pacing), keeps the copy and serves it. A failed fetch is a 404. The copies are not linked to the game record, so they never change the library or the sync timestamp.

The cover cache size and purge include the `lc-*` copies. The startup sweep keeps them out of the orphan check and instead deletes each `lc-*` copy whose URL no library game shows (its stored screenshots, or the LC catalog list of its LC thread). LC page adds (`POST /api/wishlist`) send the first post's other image URLs as `screenshots`. `_prepare_game_payload` keeps only `https://` strings (at most 20). Both saving from Add Game and installing a new game from an archive store the supplied screenshots for the matching LC thread.

`get_cover_cache_status()` returns `{success, count, bytes, running}`. `purge_cover_cache()` disables downloads for this session, clears the columns and deletes cache files under the same lock used to store them, then dispatches `wlib-refresh-library`. In-flight reads are discarded. Local user covers survive. Shutdown stops the service. Cached files and references are excluded from exports, backups and sync and never modify the sync timestamp.

### Performance and prefix tools

On Linux, launch options resolve GameMode and MangoHud per game against their global defaults. Enabled, available wrappers surround the complete game command before Cheat Engine, sandbox, network isolation, and Flatpak host wrapping. GameMode is skipped in the sandbox; MangoHud remains available. The RPGMaker Linux runner is never wrapped with `mangohud` (skip reason `NW.js hangs with it`): with MangoHud's `libMangoHud_shim.so` preload, NW.js spins one CPU core at startup and never opens a window. GameMode still applies, and arguments the user wrote that start `mangohud` (for example `mangohud %command%`) run unchanged. Browser and Windows launches skip both. Skip reasons are printed and written to the per-game debug log when enabled. Companion tools and Wine cleanup commands are not wrapped.

**Gamescope.** `core/game_launch.py` resolves the per-game `gamescope` override (`default|on|off`) with `tool_enabled("gamescope")`. When it is on, `core/gamescope.py` `resolve_options()` merges the global `gamescope_*` settings with the game's overrides (a non-empty game resolution, scaler or filter replaces the global value; game extra arguments come after the global ones) and passes them as `launcher.launch(gamescope=...)`. The launcher skips gamescope, with the reason in the print output and the per-game debug log (`Gamescope skipped: <reason>`), for Windows, a system-browser launch, the Flatpak built-in player, a wLib that runs inside a gamescope session (`steam_env.gaming_mode()`), a command prefix that already runs `gamescope` (the words before `%command%`, or a Custom Command line; game arguments do not count), or a host with no `gamescope` (`host_which`). Otherwise `gamescope_argv()` builds `gamescope [-f|-b] [-W w -H h] [-w w -h h] -S <scaler> -F <filter> [-r fps] <extra args>`. Fullscreen gives `-f`, Borderless `-b`, Window neither. The output size (`output_size()`) is the set output resolution. With both resolutions Auto, it is the screen that holds the wLib window in physical pixels (`core/display_info.py`, set by `main.py` on the GUI thread at startup and when the window changes screen), because nested gamescope 3.17 otherwise renders at 1280x720.

*Auto game size.* A set game resolution is used as it is, and no detection runs. For an Auto game resolution, the launcher's `gamescope_native_size()` calls `core/game_native_size.py` `detect_native_size(game_dir)` on the launch target's folder. It reads RPG Maker games only (the same data-root rule as `rpgm_data_root()`, so `<folder>` or `<folder>/www`): MZ from `data/System.json` `advanced.screenWidth/screenHeight`; MV (`js/rpg_core.js` present) from `SceneManager._screenWidth/_screenHeight` assignments in `js/rpg_managers.js` outside comments and quoted text, else 816x624, replaced by the last enabled known resolution plugin in `js/plugins.js` (`KNOWN_PLUGINS`: YEP_CoreEngine `Screen Width/Height`, Community_Basic `screenWidth/screenHeight`). plugins.js is parsed as JSON from the first `[` to the last `]`; no JavaScript runs. Each side must be 1..16384, and files over 2 MiB (4 MiB for plugins.js) are not read. Only regular files are read (a symlink to one counts): the open does not wait (`O_NONBLOCK` where it exists), so a named pipe or a device counts as a missing file and cannot stall the launch. Any error means no native size, and an exception from detection does not stop the launch. `gamescope.auto_game_size()` holds the fit rule: the native size is the game size when it fits inside the output size on both sides (or when the output size is not known), else the output size is used. So an unknown screen with a native size gives `-w/-h` only, and with no native size gives no size flags. The debug log has a note before the full `Gamescope: ... --` line: `Gamescope game size 1280x720 from js/plugins.js (YEP_CoreEngine)`, `Gamescope game size: no native size found, using the output size`, or `Gamescope game size: native 1920x1080 (data/System.json) is larger than the output 1366x768, using the output size`.

Gamescope goes in front of the final command, after GameMode/MangoHud, Cheat Engine and the bwrap or network-only wrapper, and before `host_command()`, so it runs on the host (Flatpak: `flatpak-spawn --host`) and is the process-group leader. Stop (`killpg`) and `group_alive()` cover gamescope, bwrap and the game. With "Run in sandbox" or "No internet", `build_bwrap_argv(..., gamescope=True)` and `build_network_bwrap_argv(..., gamescope=True)` leave out the host X sockets, the host Wayland socket and the host Xauthority, and wrap bwrap in `GAMESCOPE_BIND_SHIM`: a POSIX `sh` script that runs inside gamescope, reads `DISPLAY`, `XAUTHORITY` and `$XDG_RUNTIME_DIR/$GAMESCOPE_WAYLAND_DISPLAY`, and inserts `--ro-bind-try` binds for them at a fixed argv index (after `--tmpfs /run` in the full sandbox; only the X socket, after `--tmpfs /tmp/.X11-unix`, for the network-only wrapper). Unsandboxed plain Wine (not umu) runs as `sh -c "$GAMESCOPE_WINE_WAIT" sh <wineserver> <game>`, so gamescope stays open while a launcher stub's real game runs: after the game command exits, the script reads `/proc` once a second and waits while a process that is not a Wine background process (the `_wine_group_pids()` names, matched in any case) is in its own process group. Another game on the same prefix does not keep it open. It runs `<wineserver> -w` only when it cannot read its own `/proc/<pid>/stat`. `gamescope`, `gamescope-wl` and `xwayland` count as Wine background processes in `_wine_group_pids()`.

Winecfg and Winetricks use the same prefix and runner resolution as the runtime installers. Proton tools run through umu; Wine tools use host binaries. A plain Wine target runs the selected Wine build (a path as it is, a bare name such as `wine` from the host PATH) for Winecfg, the RTP installer and Winetricks, which gets it as `WINE` (and the `wineserver` beside it as `WINESERVER`); a selected build that is missing or not executable gives "Wine is not installed" before any work starts. Winetricks requires zenity or kdialog. Only one prefix tool can run at a time; it cannot run alongside an installer or a game using the same prefix, and installers and games on that prefix refuse while it remains open.



### Update downloads

`core/download_links.py` parses fresh first-post mirrors and the thread's `archive_password` fetched through the signed-in extension session. For F95Zone and LewdCorner alike, hidden regions (`u-hidden` on any non-void tag, `aria-hidden="true"`, and `tabindex="-1"` on links; hidden icons inside a visible link do not hide the link) are skipped, and each XenForo spoiler is its own heading scope: the label, section and download scope set inside it end where it ends (links after a `download` spoiler are read only when a download heading outside it covers them), and its button text ("Spoiler:" and the title) is not read as post text. `HOST_DOMAINS` maps host IDs to `(display_name, domains)` and `IN_APP_HOSTS` (`pixeldrain`, `mega`, `buzzheavier`) limits which hosts can run in-app; `_host_of_label` normalizes link-text words to `[a-z0-9]` against the host ID, display name, or first domain label. `classify_build` treats `apk` as `android` and `ios`/`iphone`/`ipad`/`ipa` as `ios`. `find_archive_password` scans plain-text first-post lines starting at the `DOWNLOAD` heading (then wrapping to the start) for English and Russian password labels, with a 3-line look-ahead over chrome lines, a deny list for non-passwords, quote stripping, a 128-character limit, and URL rejection. `spoiler_title_kind(title, thread_version)` reads the title as `download` (works like a bold DOWNLOAD heading), `part` ("Part 7", held like a part line), `old` (a version the thread's version does not have, compared with `normalize_version`, a date, or a word such as "old", "previous" or "legacy") or `ignore`. Builds inside an `old` spoiler have kind `old` and the spoiler title as their section, so they never merge with the current build. `core/update_downloads.py` holds link addresses only in memory, behind opaque IDs, for at most five minutes or until the picker closes; a download added to the queue keeps its link in memory until it finishes, fails for good or is removed. Links are never written to the database, exports, sync, or logs; a saved download stores only the build and mirror (`label`, `section`, `platform`, `host`, `part`, `kind`, `mirror`, `copy`) and, when non-empty, the thread's `archive_password` (refreshed on relink and deleted with the job). `core/downloads/` contains the job manager, transfer loop, and Pixeldrain, MEGA and Buzzheavier adapters. When a resolve result includes a valid `user_agent` (1–512 printable ASCII characters, `0x20`–`0x7E`), `DownloadManager` keeps it in memory alongside the resolved address (cleared by `drop_address` and never saved, logged, exported, synced, or placed in snapshots or `source`) and `network.open_host()` sets `User-Agent` on every Pixeldrain, MEGA and Buzzheavier request (metadata/API, file, and `Range` requests) when the request does not already set one; a missing or invalid value leaves urllib's default User-Agent in place. `network.cloudflare_refusal()` treats an HTTP 403 whose first 512 body bytes, stripped, start with `error code: 1010` (bounded read, error closed) as a client refusal; every host's probe and stream, MEGA's `_request`, and `transfer.open_range()` check it before host classification and raise `DownloadError("blocked by a challenge")`, which stops the job as `challenge` without retrying automatically or starting a partial transfer over. Transfers run in the background into `<data dir>/downloads/`, use temporary `.part` files and verify archive signatures before publishing the result. Pixeldrain and Buzzheavier transfers can resume: their partial file is named after the host's file ID and size (`resume-<hash>.part`), a dropped connection reconnects with an HTTP `Range` request up to three times, and a paused download or one that failed with a network error keeps its partial file so its retry continues it (a host that answers without `206`, or with another 4xx, starts over once the full download opens; when the full request also fails, for example Pixeldrain's 403 quota or captcha limit, the file is kept; a timeout or 5xx on the `Range` request fails with a network error and keeps the file). A 429 or Cloudflare 1010 on a `Range` request keeps the partial file and fails immediately (as a rate limit or challenge) instead of starting over. Removing the download, an invalid file or a full disk removes it, except when the same build and mirror is chosen again in its place (the new download continues that file) or another download of the same host file still writes it or continues from it (`transfer.delete_part` checks and deletes under the lock that a transfer takes the file with). MEGA decrypts while downloading and always starts over. Staging is device-local and excluded from backups and sync; startup removes partial files that no queued download can continue from, paused or failed file-host downloads untouched for 30 days, and archives older than seven days that no install dialog holds. Optional file-host accounts (`core/downloads/accounts.py`) make downloads use the user's quota: a Pixeldrain API key is sent as HTTP Basic auth, and MEGA sign-in stores only the session id (`sid`), never the password. The `pixeldrain_api_key`, `pixeldrain_username`, `mega_session` and `mega_email` settings are device-local and absent from the backup/sync allowlists.

`get_game_screenshots(game_id)` returns `success`, `screenshots` as `{thumb, full}` URL pairs, `source` (`catalog` or `library`), and `in_catalog`. An unknown game returns `success: false` and `error`. The catalog is read without requesting the thread or changing the library.

### Steam shortcuts and headless launches

On Linux, `core/steam_env.py` discovers native Steam, local accounts, Steam Deck and Gaming Mode. `core/steam_shortcuts.py` reads the binary shortcut file while preserving other entries. It writes through a temporary file and keeps a `.wlib-bak` copy, and writes only when the file still holds the version it read; when Steam saved it meanwhile, the sync plans again from the new file. Additions, updates and removals wait while Steam is running and until the file has been stable for five seconds after exit. A serialized GUI worker debounces sync requests from library changes and saves of the default HTML player setting, and polls pending work every 30 seconds. The mode, account, game marks and shortcut links are device-local and are excluded from library exports and sync.

At GUI startup `core/steam_script.py` refreshes `<data>/steam/wlib-steam` for the current AppImage, native launcher, Flatpak or checkout. A game shortcut passes its game ID to `--launch`, which starts the shared tracked launcher without a window or extension server. The runner remains alive through the final playtime tick and forwards stop signals. Per-game run records in `<data>/runs/` let an open window show and stop a runner; process locks prevent concurrent launches. Stale records are discarded. Failures are shown in the open window, or a GUI child opens to show them. Before it starts the game the runner asks an open window (`POST /api/launch-check`) whether the game is busy (install, restore, mod tool), whether a prefix tool or runtime install holds its prefix, and whether a running game blocks the prefix; the window holds that prefix until the runner reports `ended` or `error`. Each runner invocation sends a unique `launchId` with the check and its events, and the window releases a reservation only for the invocation that made it, so a refused duplicate launch cannot free the running game's prefix. Each runner also claims its Wine prefix in its run record (under a lock shared by all runners) before the game starts and holds it until the record goes, so runners started with the window closed refuse a prefix a game of another runner cannot share, and a window opened later sees those claims. Games share a prefix under the same rules as in one launcher. The runner starts the game without this check only when no wLib listens (connection refused). A timeout (10 seconds), an error status or a bad answer refuses the launch; while the window has not made its `Api` yet, the endpoint answers 503 so the runner refuses and the user can try again. The runner endpoints (`/api/running`, `/api/launch-check`, `/api/runner-event`) require the `X-wLib-Runner` token from `<data>/runner-token` (mode 0600), which a sandboxed game cannot read.

Shortcut link states include `linked`, `pending_add`, `pending_update`, `pending_removal` and `user_removed`. A shortcut removed in Steam stays removed until the mark is toggled or the user selects Sync now. Artwork is generated from the local or cached cover without network access: a 600×900 portrait, 920×430 capsule and 1920×620 hero. The source filename and mtime avoid unnecessary rewrites. Covers Qt cannot decode (AVIF) are queued; the window converts them to PNG (`wlib-steam-covers` event, `get_steam_cover_conversions`, `save_steam_cover_png`) into the device-local `covers/cache/steam-png/`, and the next sync uses that copy. A game waiting for conversion gets its shortcut without artwork until then. Flatpak host launches forward Steam's overlay and app ID environment; overlay and focus under Flatpak remain experimental.

### Storage usage and cleanup (`core/storage_usage.py`, `core/storage_cleanup.py`, `core/api_mixins/storage.py`)

- **Measurement engine (`core/storage_usage.py`)**: `measure(path, budget) -> Measure(bytes, files, skipped)` measures allocated size on disk rather than apparent file length. On POSIX it runs an iterative `os.scandir` walk using `st_blocks * 512` for files and folders (the same total as `du`), never follows symlinks, never crosses mount points (`st_dev` check), counts unreadable entries as `skipped`, checks its `threading.Event` cancel flag per directory, and de-duplicates hard links (`st_nlink > 1`) across the scan with a `(st_dev, st_ino)` set. On Windows it walks folder handles with `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` (256 KiB buffer), never enters reparse points, falls back to `FileStandardInfo` for WOF-compressed files (`AllocationSize == 0` with `EndOfFile > 0`), and de-duplicates `FileId` per measured root. Worker threads lower priority via `low_priority_thread()` (Linux `ioprio_set` idle class + `setpriority(19)` per thread ID; Windows `THREAD_MODE_BACKGROUND_BEGIN`), logging and continuing on failure.
- **Game root detection & device-local picked folders**: `storage_root(game, ctx)` is read-only and separate from uninstall's `detect_root()`. Order: (1) a user-picked folder from device-local `<data dir>/storage-roots.json` when it still holds the executable and passes the guard; (2) the library folder pattern destination when it holds the executable and passes the guard; (3) for an executable inside a library folder `L`, climb up below `L` while no parent holds another game's executable; (4) outside library folders, climb only through known sub-folders (`bin`, `bin64`, `Binaries`, `Win64`, `Win32`, `x64`, `x86`, `x86_64`, `lib`, any case) plus one step when the parent holds `Engine`; (5) otherwise the executable's folder marked `uncertain`. Every result (including picked folders) must pass the guard refusing library folders, drive/filesystem roots, the home folder, and folders holding another game's executable (`unsafe` with no game unit). Unavailable folders keep their previous report size (`unavailable`). `storage-roots.json` is written atomically, pruned when games are removed, and is strictly device-local (never exported or synced).
- **Scan service, report & optional recount**: `StorageScanService` runs one worker thread under a shared `task_lock`, builds a de-duplicated unit plan (shared game folders count once in totals with `shared_with` notes; single-game custom prefixes attach to that game while multi-game custom prefixes stay in `wine_prefixes`; torrent data attaches as `torrent_bytes` outside the game sum), and writes `<data dir>/storage-report.json` (`version: 1`) atomically. `storage-report.json` is device-local (never exported or synced). Starting a game (`launch_game`, `reserve_runner_launch`) stops any active scan or recount (`stopped_reason: "game"`), keeping the previous report; starting a scan while `get_running_games()` is non-empty is refused. Archive install, update, move, uninstall and game removal call `game_changed(game_id, kind)`: install, update, move and uninstall mark the row changed (uninstall also takes the deleted game folder out of the sizes); removal drops the row and moves its sandbox and player sizes to the removed-game data. The device-local setting `storage_recount_after_changes` (default off, excluded from `GENERAL_SETTINGS_KEYS`, exports and sync) triggers a low-priority single-game recount on install, update or move when a report exists, `power.on_battery()` is not `True`, no game runs, and no full scan is active.
- **Cleanup actions (`core/storage_cleanup.py`)**: `StorageCleanupService` shares `task_lock` with `StorageScanService` (no scan and cleanup simultaneously). `preview(action)` re-lists and measures targets and stores a random token for 15 minutes; `run(preview_id)` drops expired previews, re-checks blocked conditions, re-lists targets, intersects with the preview, verifies every target sits strictly inside its allowed root(s) without following symlinks, deletes with `os.unlink` / `shutil.rmtree`, and updates `storage-report.json` in place:
  - `download_archives` (`<data dir>/downloads/`): finished files only; protects `.part` files, archives open in `DownloadManager`, archives of `READY` download queue jobs, the `rpgm-*` archives of a running RPG Maker runner or mkxp-z install, and the `downloads/torrents/` folder.
  - `unpack_leftovers` (`<data dir>/install-scratch/`): direct children; blocked while an archive install or RPG Maker runner preparation runs.
  - `removed_game_data` (`<data dir>/sandbox/removed/`, `<data dir>/web-player/removed/`): direct children; confirmation warns that removed game data can hold saves.
  - `save_backups` (`<data dir>/save-backups/<game id>/`): backups older than `save_backup_keep` via `list_backups()[keep:]`; blocked when set to "Keep all", and skips games with an active save operation or protected backups.
  - `proton_builds` (`<data dir>/proton/`): builds not used by any game's `proton_version` or the `proton_path` default setting (never touches Steam, Lutris or umu folders); blocked while any game started by wLib runs.
  - `cover_cache` (`<data dir>/covers/cache/`, `<data dir>/covers/cards/`): runs through `purge_cover_cache()` so database references stay consistent and user-chosen local covers in `<data dir>/covers/` stay untouched.
  - `bepinex_cache` (`<data dir>/bepinex-cache/`): direct children; blocked while a BepInEx install or update runs.
- **Bridge (`core/api_mixins/storage.py`)**: exposes `get_storage_state`, `start_storage_scan`, `stop_storage_scan`, `preview_storage_cleanup`, `run_storage_cleanup`, `set_storage_game_folder`, `clear_storage_game_folder`, and `open_storage_location`.
